# PepeEdtaBot

[![CI](https://github.com/fdlone/PepeEdtaBot/actions/workflows/ci.yml/badge.svg)](https://github.com/fdlone/PepeEdtaBot/actions/workflows/ci.yml)
[![License: MIT](https://img.shields.io/badge/License-MIT-blue.svg)](LICENSE)

> **EN:** A Telegram group-chat bot that learns from the chat's own messages and
> replies via a per-chat Markov chain — fully algorithmic, no LLM. Chat mood
> tracking, context-aware candidate scoring with Russian stemming, a
> "personality" layer (chat-local memes, emoji, rare form breaks, regulars'
> quirks). Stored text is stripped of links, `@mentions` and recognized personal
> data, authors are anonymized, ids are HMAC hashes. Python 3.12+, aiogram 3,
> SQLite. Docs are in Russian — start with
> [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md).

Telegram-бот для группового чата. Учится на сообщениях чата и генерирует ответы
на цепях Маркова — полностью алгоритмически, без внешней LLM.

## Что умеет

- **Генерация ответов** — пер-чатовая цепь Маркова 3-го порядка с бэкоффом до
  2-го; best-of-N конвейер: несколько кандидатов, скоринг (завершённость, длина
  по режимам short/medium/long, IDF-релевантность контексту со стеммингом
  русской морфологии, штрафы за повторы и дословное цитирование), softmax-отбор.
- **Ответы «в тему»** — сообщение, на которое отвечают, задаёт контекст:
  якорение стартовых состояний, биас по стемам, дословные цитаты корпуса
  достраиваются «отсебятиной» вместо отбраковки; позиция контекстного якоря
  варьируется — часть ответов подхватывает тему серединой или концом.
- **Настроение чата** — sleepy/calm/lively/heated из темпа сообщений и
  эмфатики; модулирует вероятность ответа, вариативность, длину и flavor. Серия
  прямых обращений «заводит» бота.
- **AI-директор ответов** — вероятность самостоятельного ответа следует за
  моментумом беседы (бёрсты после ответа, суточные капы, анти-флуд обращений).
- **Слой «личности»** — эмодзи из словаря конкретного чата, «локальные мемы»
  (горячие n-граммы последних дней сидируют ответы), редкие сломы формы
  (вердикт/КАПС/двойное сообщение/фальстарт), причуды для завсегдатаев («опять
  ты» отдельным сообщением перед ответом).
- **`/pivo`** — шуточный созыв в Discord по opt-in подписке с анти-повтором
  шаблонов и временными вариациями (ночь/пятница/понедельник).

Как это устроено внутри — [`docs/GENERATION_PIPELINE.md`](docs/GENERATION_PIPELINE.md)
(путь сообщения от хендлера до ответа) и
[`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) (слои, данные, приватность).

## Стек

- Python 3.12+ (CI прогоняет матрицу 3.12 / 3.13 / 3.14)
- aiogram v3
- SQLite + aiosqlite
- `cryptography` (Fernet для `/pivo`, HKDF для вывода ключей)
- конфигурация через `.env`

## Быстрый старт

```bash
python -m venv .venv
.\.venv\Scripts\activate
pip install -r requirements.txt
```

1. Создайте `.env` на основе [`.env.example`](.env.example) — там описан каждый
   параметр, его назначение, дефолт и границы.
2. Заполните `BOT_TOKEN`, `PIVO_HMAC_SECRET`, `PIVO_ENCRYPTION_SECRET`
   (секреты — не короче 32 символов, иначе бот не стартует; как их
   сгенерировать и чем грозит смена — в
   [`docs/OPERATIONS.md`](docs/OPERATIONS.md)).
3. Опционально задайте `OWNER_ID`.
4. Запустите:

```bash
python main.py
```

Отключите privacy mode у бота в BotFather, иначе бот не увидит сообщения группы:
`Bot Settings -> Group Privacy -> Turn off`.

## Docker

```bash
docker build -t pepe-bot:latest .
docker run -d --name pepe-bot --env-file .env -v ${PWD}/data:/app/data pepe-bot:latest
```

Через Compose ([compose.yaml](compose.yaml)):

```bash
docker compose up -d --build   # запуск/пересборка
docker compose down            # остановка
```

Контейнер стартует как `root`, приводит владельца `/app/data` к пользователю
`bot` (UID 1000) и сбрасывает привилегии — это нужно, когда хостовая `./data`
принадлежит другому UID/GID. Если она уже принадлежит UID 1000 (или используется
named volume), запускайте с `--user 1000:1000`. Устройство образа —
[`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md#docker).

## Команды

Команды предназначены для групповых чатов. Личный чат с ботом не является
поддерживаемым рабочим сценарием.

| Команда | Кому доступна | Что делает |
|---|---|---|
| `/help` | всем | список команд |
| `/ping` | всем | проверка, что бот онлайн |
| `/stats` | всем | статистика модели по текущему чату |
| `/config` | всем | основные действующие настройки чата |
| `/config full` | админам чата и `OWNER_ID` | полный список настроек; отказ отвечается явно, краткая форма молча не подставляется |
| `/pivo [время] [повод] [@кого]` | всем | позвать в Discord шуточным сообщением |
| `/pivo_on` / `/pivo_off` | всем | включить/выключить себя в списке упоминаний `/pivo` |
| `/pivo_privacy` | всем | что именно хранится для `/pivo` |
| `/set <key> <value>` | админам чата и `OWNER_ID` | изменить настройку **в этом чате** (`/set help` — подсказка) |
| `/set global <key> <value>` | только `OWNER_ID` | изменить глобальное значение |
| `/set reset <key>` | админам чата и `OWNER_ID` | вернуть чат к глобальному значению |
| `/setprob 0.2` | те же, что у `/set` | быстрый setter вероятности ответа (`/setprob global 0.2` — во всех чатах) |
| `/clear confirm` | админам чата и `OWNER_ID` | очистить все данные текущего чата |
| `/pivo_check` | только `OWNER_ID` | диагностика упоминаний `/pivo`: каким путём построено упоминание каждого подписчика и почему; ответ намеренно без разметки упоминаний, чтобы никого не пингнуть |
| `/quirk_stats` | только `OWNER_ID` | достижим ли в чате порог «завсегдатая»: сколько людей имеют счётчик, максимум, сколько перешагнули порог. Только числа — счётчики анонимны |

Изменения через `/set` живут до перезапуска процесса и хранятся по чатам:
чат, о котором бот давно не слышал, возвращается к глобальным значениям вместе с
остальным своим состоянием. `/config` показывает эффективные для чата значения и
отмечает переопределённые.

`/clear confirm` стирает модель, сообщения, эмодзи-статистику, горячие
n-граммы, счётчики взаимодействий, а также подписки `/pivo` и их квоты. Команда
чат-скоуплена: процесс-глобального эффекта у неё нет.

После каждого `/pivo` владелец (`OWNER_ID`) получает в личку короткий отчёт:
название чата и сколько подписчиков упомянуто каким путём. Тот же агрегат идёт в
лог; личка нужна потому, что решение принимает владелец, а логи ему недоступны.
Выключается `PIVO_REPORT_TO_OWNER=false`; сбой доставки на работу `/pivo` не
влияет.

По той же причине владелец получает в личку сигнал, если обслуживание базы
перестало проходить: снаружи это выглядит как «бот жив, просто мемы перестали
выветриваться», и без сигнала замечается через недели. Сообщение уходит не
раньше чем через час непрерывных неудач (разовая — это обычный бэкап или
`VACUUM`), напоминание повторяется не чаще раза в сутки, а починка отмечается
отдельным сообщением. Без `OWNER_ID` сигнал никуда не идёт; сбой доставки
гасится и на ответы с обучением не влияет.

**Лимиты.** Команды ограничены по частоте на пару «участник + чат»: дешёвые
ответы из памяти (`/help`, `/ping`, `/config`, `/pivo_privacy`) — 15 с, чтение
из базы (`/stats`) — 60 с, запись (`/pivo_on`, `/pivo_off`) — 30 с, `/clear` —
час. Превышение по умолчанию игнорируется молча; там, где человек ждёт
подтверждения (`/clear`, `/pivo_on`, `/pivo_off`), бот отвечает, сколько
осталось ждать, но не чаще раза в 30 секунд — иначе отказ сам становится
потоком сообщений. Owner-only команды и `/pivo` намеренно без окна: у `/pivo`
своя суточная квота (3 вызова, 5 для админа и владельца), а троттлинг глушил бы
вызов до хендлера, и вместо «лимит исчерпан» человек получал бы тишину.

## `/pivo`

Работает строго по opt-in: без явных упоминаний бот зовёт только тех, кто сам
включил себя командой `/pivo_on`. Все команды `/pivo*` доступны только в группах
и супергруппах.

```text
/pivo
/pivo 20:00
/pivo watch movie
/pivo 20:00 watch movie @friend
```

Если в команде есть явные `@mentions`, бот уведомит только их; иначе берётся
текущий список подписчиков.

Два предела работают по-разному и намеренно. Явных упоминаний нельзя указать
больше `PIVO_EXPLICIT_MENTIONS_LIMIT` — вызов отклоняется с объяснением: список
перечислил сам вызывающий, и молчаливое усечение скрыло бы, что часть названных
не позвана. Список подписчиков, наоборот, усекается до
`PIVO_SUBSCRIBER_FANOUT_LIMIT` с пометкой в сообщении, что упомянуты не все:
отказ ломал бы команду для всего чата навсегда — достаточно было подписаться
сверх предела.

Время распознаётся только в начале аргументов (`20:00`, `сегодня/завтра 21:00`,
`вечером` и комбинации), всё остальное считается описанием повода. Повод и время
режутся по длине (200 и 40 символов): иначе достаточно длинный аргумент делал
сообщение длиннее лимита Telegram и отправка падала при каждом вызове.

## Данные и приватность

- Хранится не сырой текст: перед записью удаляются ссылки, `@упоминания` и
  распознанные персональные данные, схлопываются пробелы. Результат
  (`messages.normalized_text`) живёт в пределах окна ретенции — последние
  `MESSAGES_RETENTION_PER_CHAT` сообщений чата.
- Авторы анонимизированы, идентификаторы хранятся только как HMAC-хэши,
  `chat_id` в логах маскируется.
- Всё стирается `/clear confirm`; `/pivo_privacy` показывает пользователю, что
  именно хранится для подписки.

Механизмы целиком — [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md#приватность-и-безопасность),
операционная часть (секреты, бэкапы, retention) —
[`docs/OPERATIONS.md`](docs/OPERATIONS.md).

## База данных

- Runtime/Docker база по умолчанию: `data/markov.db` (volume `./data:/app/data`).
- Корневой `markov.db`, если он есть, — локальная тестовая база, не боевая.
- Существующие базы мигрируются автоматически при запуске.
- Полностью чистый старт: остановить бота, удалить `data/markov.db` вместе с
  `-wal` и `-shm`, запустить снова.

Синтетические данные для локального smoke-теста:

```bash
python -m tools.seed_db --db markov.db
python -m tools.seed_diverse --db markov.db
```

## Разработка и тесты

Проект использует стандартный `unittest` (без pytest), `ruff` и `mypy strict`.
Источник истины по зависимостям — `requirements*.txt`/`.lock` (pip); `uv` можно
использовать как локальный раннер, но lock он не ведёт.

```bash
pip install -r requirements-dev.txt

python -m ruff check app/ tests/ tools/ main.py
python -m mypy app/
python -m unittest discover tests -v
```

Статическая проверка типов охватывает только `app/` — это принятое ограничение,
не недосмотр: расширение на `tests/` и `tools/` даёт сотни ошибок и является
самостоятельной задачей. Состав CI —
[`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md#тесты-и-ci).

Для отладки генерации: `GEN_TRACE_LOG=true` включает пошаговый трейс отбора
кандидатов независимо от `LOG_LEVEL`, а `tools/eval_generation.py` /
`tools/eval_prod.py` дают синтетический и продовый eval конвейера (см.
[`docs/GENERATION_PIPELINE.md`](docs/GENERATION_PIPELINE.md)).

Эволюция генератора (Markov 2.0R) идёт по нормативному пакету
[`docs/v2/`](docs/v2/) через eval-протокол: `python -m tools.eval` — ablation-
матрица C0–CF, метрики с доверительными интервалами, предрегистрированные
гейты фаз ([`tools/eval/README.md`](tools/eval/README.md)); отчёты — в
`docs/eval_reports/`. Property-тесты инвариантов пишутся на `hypothesis`
(dev-зависимость).

Фаза 9 (`MARKOV_INTERP_ORDER2_WEIGHT`, дефолт 0) добавляет мягкую интерполяцию
шага с проекцией order-2 — единственный механизм пакета, который не
переваживает существующих кандидатов, а создаёт новых: на этом корпусе 97.5%
состояний order-3 предлагают ровно одно продолжение, из-за чего энтропийная
температура и временнáя смесь измерились инертными. Перепись состояний и
симуляция эффекта воспроизводятся на любой копии БД:
`python -m tools.eval.state_census --beta 0.3`.
