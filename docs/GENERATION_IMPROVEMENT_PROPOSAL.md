# Предложение по улучшению генерации ответов

> Автор: аудит-сессия 2026-06-20
> Объект: движок генерации `markov.py` и пайплайн ответа в `app/handlers/learning.py`
> Статус: предложение (изменения в код не вносились)

## 1. Контекст и цель

Бот генерирует ответы цепями Маркова порядка 1–3 с backoff'ом, контекстным
смещением (reply-context bias), штрафами за повторы, «прыжками» (jump/restart)
и многоступенчатой валидацией результата. Логика рабочая и довольно зрелая, но
обладает двумя системными ограничениями:

1. **Нет объективной метрики качества.** Поведение управляется ~20 подобранными
   вручную константами, разбросанными по коду. Любая их правка делается вслепую —
   нельзя сказать, стало ли «лучше».
2. **Стоимость генерации не наблюдается и потенциально высока** из-за вложенных
   циклов ретраев.

Цель документа — предложить план, который делает качество **измеримым**, правки
**безопасными**, а сам движок — **более естественным и релевантным** входящему
сообщению.

## 2. Анализ текущего состояния

### 2.1. Управляющие параметры разбросаны по коду

Примеры «магических» констант, напрямую влияющих на стиль ответа:

| Где | Константа | Смысл |
|---|---|---|
| `markov.py:572-576` | `next_explore = 0.12 + 0.18*strength` | вероятность случайного выбора токена |
| `markov.py:573` | `next_power = 0.72 - 0.16*strength` | «температура» (степень для частот) |
| `markov.py:576` | `jump_probability ≤ 0.32` | вероятность перезапуска цепи |
| `markov.py:295` | `/ (1 + repeat*0.85*penalty)` | штраф за повтор токена |
| `markov.py:297` | `* (1 - 0.96*penalty)` | штраф за немедленный повтор |
| `markov.py:306` | `* (1 - 0.94*penalty)` | штраф за повтор тройки |
| `markov.py:253` | `0.92 ** step_index` | затухание контекстного смещения |
| `markov.py:438/480` | `recency_bonus 0.35 / 0.30` | бонус свежим окнам контекста |

Менять их по одной, проверяя «на глаз» в чате, — основной источник риска регрессий.

### 2.2. Мультипликативное раздувание ретраев

- В хендлере: `MAX_GENERATION_ATTEMPTS(4) + MAX_TRAINING_PREFIX_RETRY_ATTEMPTS(6) = 10`
  внешних попыток (`learning.py:232-235`).
- Внутри каждой `generate_text` крутит `VALIDATION_RETRY_ATTEMPTS = 8`
  (`markov.py:531`).

В худшем случае это **до ~80 полных генераций на одно сообщение**, каждая с
обращениями к кэшу/БД. Реальное распределение сейчас никак не измеряется.

### 2.3. Токенизация теряет часть стиля чата

`TOKEN_RE = r"\w+|[.,!?;:]"` (`markov.py:11`):

- теряет эмодзи и спецсимволы (важная часть стиля чат-сообщений);
- рвёт слова с апострофом (`don't` → `don`, `t`);
- не различает экспрессивную пунктуацию (`!!`, `?!`, `...`).

### 2.4. Естественность вывода

`detokenize` (`markov.py:22`) не капитализирует начала предложений, а
`normalize_lower` приводит всё к нижнему регистру — ответы выглядят «телеграфно».

### 2.5. Стратегия выбора — «первый подходящий»

Кандидат принимается первым, как только прошёл валидацию
(`learning.py:287-296`). При этом часть вычислений на отбраковку уже потрачена —
их можно переиспользовать как **ранжирование**, а не бинарный фильтр.

### 2.6. `markov.py` вне статических проверок

Модуль исключён и из `ruff`, и из строгого `mypy` (`pyproject.toml`). Это самый
сложный и часто правимый файл — отсутствие типов повышает риск регрессий именно
там, где будут идти доработки.

## 3. Предлагаемый план

Этапы упорядочены так, чтобы каждый следующий опирался на измеримость,
введённую предыдущим.

### Этап 0 — Подготовка к безопасным правкам

**0.1. Завести `markov.py` под `ruff` + строгий `mypy`** (инкрементально).
Сначала исправить `UP045` (`Optional[X]` → `X | None`) и проставить типы, затем
убрать модуль из списка исключений в `pyproject.toml`. Даёт страховку для всех
последующих этапов.

### Этап 1 — Сделать качество измеримым (фундамент)

**1.1. Оффлайн-харнесс оценки.** Скрипт (`tools/eval_generation.py`), который на
фиксированном корпусе/seed-БД генерирует N ответов и считает:

- `distinct-1`, `distinct-2` — лексическое разнообразие;
- долю повторяющихся биграмм/триграмм;
- среднюю и медианную длину ответа;
- % пустых результатов (`generate_text` вернул `""`);
- % verbatim-копий обучающих сообщений;
- распределение использованного порядка (3/2/1) и числа jump'ов;
- среднее число попыток до принятия (см. 1.2).

Фиксируем `random.seed` для воспроизводимости. Это baseline, относительно которого
сравниваются все дальнейшие изменения.

**1.2. Инструментировать пайплайн счётчиками.** Возвращать из `generate_text`
(или логировать на DEBUG) число использованных попыток, выбранный порядок,
jump_count. Питает и харнесс (1.1), и продовые метрики (этап 4).

### Этап 2 — Централизовать параметры

**2.1. `GenerationProfile`.** Собрать константы из раздела 2.1 в один frozen
dataclass (по образцу `config_registry.py`). `generate_text` принимает профиль
вместо россыпи аргументов. Эффект:

- харнесс из 1.1 может перебирать профили и искать лучшие значения;
- часть параметров можно безопасно вынести в `/set`.

### Этап 3 — Улучшить сам алгоритм (по данным харнесса)

**3.1. Сократить раздувание ретраев** (раздел 2.2): по данным 1.2 схлопнуть
двойной цикл или сделать эскалацию случайности сквозной (без перезапуска счётчика
во внутреннем цикле). Цель — снизить потолок генераций на сообщение без потери
качества по метрикам 1.1.

**3.2. Ранжирование кандидатов** (раздел 2.5): генерировать K кандидатов и
выбирать лучший по скору = релевантность к входящему сообщению − штраф за
повторы. Переиспользовать `is_low_diversity_reply` / `is_context_heavy_reply` как
компоненты скора, а не как бинарный фильтр.

**3.3. Улучшенная токенизация** (раздел 2.3): поддержать эмодзи, апострофы,
кратную пунктуацию; добавить тесты. Внимание к обратной совместимости модели —
изменение токенизации меняет ключи в таблицах переходов (нужна стратегия:
дотренировка / миграция / сброс на чат).

**3.4. Естественность вывода** (раздел 2.4): капитализация начала предложений в
`detokenize`/финальном тексте; опционально — лёгкая модель регистра.

### Этап 4 — Наблюдаемость в проде

**4.1. Метрики/structured logging** (перекликается с открытым AUD-006): счётчики
доли пустых ответов, использованного порядка, числа попыток, латентности
генерации. Позволяет видеть деградацию качества на реальном трафике.

## 4. Приоритеты и порядок

| Приоритет | Задачи | Обоснование |
|---|---|---|
| 🔴 Сначала | 0.1, 1.1, 1.2 | без измеримости и типобезопасности правки рискованны |
| 🟠 Затем | 2.1, 3.1 | централизация параметров + дешевизна генерации |
| 🟡 Потом | 3.2, 3.3, 3.4 | прирост качества и естественности по данным |
| 🔵 Параллельно | 4.1 | наблюдаемость в проде |

**Рекомендуемый первый шаг:** Этап 0.1 + Этап 1 (харнесс + инструментация).
После этого все дальнейшие изменения принимаются на основе чисел, а не ощущений.

## 5. Риски и совместимость

- **Изменение токенизации (3.3)** несовместимо с уже накопленной моделью:
  изменятся ключи переходов. Нужна явная стратегия (дотренировка поверх,
  миграция, или сброс модели по чату с предупреждением).
- **Вынос параметров в `/set` (2.1)** расширяет поверхность рантайм-конфига —
  обязательна валидация диапазонов (как уже сделано в `config_registry.py`).
- Все правки движка должны сопровождаться прогоном харнесса (1.1) и
  существующего `unittest`-набора, чтобы ловить регрессии числом, а не вручную.

## 6. Definition of Done для движка

Изменение в генерацию считается завершённым, когда:

1. прогнан харнесс 1.1, метрики приложены к PR (было/стало);
2. `ruff`, `mypy` (включая `markov.py` после 0.1), `unittest` — зелёные;
3. новые ветви логики покрыты тестами;
4. при изменении формата модели описана стратегия совместимости (раздел 5).
