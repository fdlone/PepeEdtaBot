# PepeEdtaBot — Pepe Response Engine (PRE) Roadmap

**Статус:** Proposed, **v1.6 (самодостаточная; заменяет v1.1–v1.5)**
Входы: eval-отчёты фаз 0–7 Markov 2.0R, census прод-копии,
`REVIEW_2026-08-13.md` (разведки R1–R4), `GENERATION_MAP.md` (карта),
внешнее ревью роадмапа и ответ рецензента (2026-08-13, сходимость).
**Scope:** эволюция генерации после Markov 2.0R: выход из измеренного
детерминизма корпуса + устранение системных искажений, найденных картой.

**Конституция (постоянная):**
1. Генерация и ранжирование чисто статистические; без LLM, embeddings,
   нейросетей и внешних AI API, включая локальные модели.
   Retrieval-статистика (BM25/TF-IDF/инвертированный индекс) разрешена.
2. **PRE оптимизирует branching пространства кандидатов, а не следующего
   токена.** Доказано фазами 2/3/7 (token-level инертен) против C4 и
   candidate-механизмов (работают). Markov — один из генераторов
   предложений внутри PRE, а не вся архитектура.
3. Правки поведения — только через OpenSpec; гейты пре-регистрируются в
   `eval_thresholds.yaml` до прогонов и не меняются после; «закрыто с
   цифрами» — полноценный результат.

**Нумерация задач:** M3R-xxx (диапазоны M2R заняты 2.0R и Phase 9).

## 0. История версий и ключевые решения

- **v1.1** — базовая структура этапов; развилки D1–D4 закрыты разведками
  R1–R4 (вырождения ансамбля нет: 4.4–4.7 уникальных траекторий из 5;
  seeded топят финализация −0.29 и verbatim; ко-оккуренсы расстояния 1 уже
  существуют; девятку мемов скорер не видит — лотерея поддержки 1).
- **v1.2** — по `GENERATION_MAP.md`: добавлен этап гигиены измерений
  (двухрежимный протокол ctx/noctx, наблюдаемость пустых каналов,
  детерминизм, пакетная перезаморозка hash); Phase 9 получила
  noctx-амендмент.
- **v1.3** — по внешнему ревью: два трека с правилом независимости,
  Structural Escape Gate, атрибуция маршрутов, таксономия отказов,
  coverage в гейтах, retrieval как маршрут, ранний пилот ассоциаций.
  **Отклонено с обоснованием:** (а) критика «ECB не ловит общий префикс» —
  ECB определена через edge-overlap и ловит его по построению (R1);
  реальный дефект — отсутствие условия качества — исправлен Escape-метрикой;
  (б) «маршруты раньше всего» в полном объёме — фразовый маршрут ждёт
  данных (132 фразы против порога 1000), это физика накопления; Track B
  фактически стартует в день деплоя (Phase 9 = smoothed-маршрут, seeded
  чинится первым пакетом). Рецензент обе поправки принял.
  **Основание поправки (б) отпало 2026-08-23** (см. v1.6): 132 фразы — census
  окна ретенции, а не корпуса, и рецензент со своим «маршруты раньше всего»
  был прав по существу. Запись оставлена как есть намеренно: отказ был
  вынесен на этом основании, и переписывать его задним числом значило бы
  спрятать, чего стоила ошибка в источнике числа.
- **v1.4** — по ответу рецензента: правило независимости треков —
  нормативное с предупреждением агентам; M3R-011 репортит пару метрик
  (ECB по пулу + escape по окну); критерий качества оконно-относительный,
  не абсолютный порог (скоры не калиброваны абсолютно, шкала различается
  между режимами — map §1.2); пилот M3R-200 получил чек-лист и лестницу
  «пилот ≠ промоушен».
- **v1.5** — самодостаточность: все секции, ссылавшиеся на прошлые версии,
  инлайнены полностью; содержательных изменений нет.
- **v1.6** (2026-08-23) — исправлена посылка фразового маршрута и снята его планка. Планка
  «≥1000 фраз cnt≥3» сверялась с census окна ретенции (132 фразы), тогда как
  фразы живут во всевременной цепи: `transitions` — это `(w1,w2)→w3` со
  счётчиком, то есть контентная триграмма как есть, а биграмма — сумма группы
  по `w3`. Замер на прод-копии даёт **831 фразу cnt≥3 уже сегодня**. Отсюда
  две правки: зависимость «фразовый маршрут ждёт откорма» снята как
  фактически неверная, а M3R-000 переопределён с накопителя на производный
  индекс с бэкфиллом. Замер воспроизводим: `python -m tools.eval.phrase_census`.
  Вторым заходом (после реализации M3R-000) снята и сама планка «≥1000 фраз»:
  тот же замер показал, что решающее число — не количество фраз, а доля входов,
  до которых маршрут дотянется (3.1% состояний при cnt≥3 против 8.4% при
  cnt≥2). Порог поддержки переведён из условия старта в плечо грида маршрута.
  Пре-регистрированных порогов правка не двигает: в `eval_thresholds.yaml`
  планки по фразам нет.

## 2. Вычеркнуто (с основаниями)

| направление | причина |
|---|---|
| нейро-реранкер, малый Transformer, любые локальные модели | конституция; ресурсов на хостинг/аренду нет |
| class-based Markov | словарь чата 3131 токен — кластеризация даст шум; бедный аналог уже есть (стеммер `morphology.py`) |
| chunk-Markov как замена единицы генерации | ADR-016: rebuild невозможен; фразовый слой допустим только как параллельный маршрут |
| order-4, temperature/entropy tuning поверх текущей цепи, anti-cycle | закрыты гейтами Phase 7/2/6 с цифрами |
| компрессия счётчиков как способ создать ветвление | измерено: 0 пулов в среднюю зону |
| иерархический выбор «режима высказывания» | требует данных о режимах, которых нет; не раньше зрелого фразового слоя |
| наращивание `CANDIDATE_TARGET` ради разнообразия | R1: добавятся глобальные обходы (win 0.141) + латентность; разнообразие уже на потолке |
| ансамбль ради числа маршрутов | R1: 4.4–4.7 из 5 уже уникальны; резерв — в качестве, не в числе |

## 3. Оценка качества без панели рейтеров (кросс-катящее)

Панель из ≥3 рейтеров недоступна (участники не заинтересованы; agreement
0.17 в Phase 4 показал цену случайной панели). Три опоры:

- **M3R-020 — соло-протокол слепой оценки (S).** Инструмент подаёт
  владельцу перемешанные неподписанные ответы (руки + C0 + декои);
  валидность — само-консистентность: ≥20% выборки предъявляются повторно,
  порог согласия с собой ≥ 0.8, иначе раунд не засчитывается и рубрика
  дорабатывается. Объём: ≥30 ответов на руку.
- **Живой сигнал реакций.** Phase 8 роадмапа 2.0R (M2R-800/810:
  отложенный агрегированный reward + бандит) **поднята из P3 в P1**:
  единственный масштабируемый датчик качества, оставшийся проекту.
  Reward-агрегат используется и бандитом, и как A/B-метрика включённых
  конфигураций во времени (L).
- **M3R-021 — таксономия отказов (S).** Классы поверх существующих причин
  трассы и гейтов: F1 нерелевантен, F2 копия контекста, F3 генеричен,
  F4 несвежий, F5 промах локального мема, F6 структурный повтор,
  F7 малформирован, F8 схлопывание маршрутов, F9 ошибка скорера.
  Телеметрия отклонений и рубрика M3R-020 размечаются этими классами;
  каждый OpenSpec-чейндж фичи заявляет целевые классы.

Автоматические прокси первичны; ручная/живая оценка — подтверждающая.

## 4. Шаблон гейта PRE

Каждый гейт фиксирует до прогона: (а) метрики качества с порогами и
значимостью (CI 95%, интервал исключает 0); (б) **coverage** —
минимальную долю ответов, которую дельта затрагивает (лекарство от
«+10% на 0.5% ответов»); (в) латентность: база 150 мс p95, превышение
допустимо только при значимом улучшении ≥ порога, зафиксированного до
прогона (по умолчанию affinity_without_copy Δ ≥ +0.05 значимо) — плохой
trade-off = отказ, хороший = поднятие бюджета решением владельца в
вердикте; (г) оба режима ctx/noctx с весом по измеренной прод-доле;
(д) ECB/Escape-инварианты (§ Track B, M3R-011).

## 5. Два трека и правило независимости

**Track A — ремонт и валидация:** гигиена измерений, seeded-корректность,
наблюдаемость, детерминизм, чистка (Этапы 1.5 и 2).
**Track B — структурный выход:** маршруты и их гейты (Phase 9, M3R-000,
011, 103, 200, 210, 220, 300).

**Нормативное правило:** Track A и Track B планируются и исполняются
независимо; зависимости между ними — явные, поимённые и минимальные.
Жёстких зависимостей четыре, и все — содержательные, не «сначала
отполируем»:

| зависимость Track B | от чего | почему |
|---|---|---|
| гейты маршрутов | M3R-140 | без второго режима гейт слеп на половину прода |
| seeded-маршрут в ансамбле | M3R-101(+144, одна перезаморозка) | иначе маршрут меряется с гандикапом −0.29 |
| ~~фразовый маршрут (полный)~~ | ~~откорм M3R-000 до ≥1000 фраз~~ | **зависимость снята 2026-08-23:** физики накопления здесь нет — фразы уже в `transitions`, их 43 229. Сама планка тоже снята: она мерила предложение, а решает отбор. Порог поддержки стал плечом грида маршрута, покрытие входов — 3.1% при cnt≥3 против 8.4% при cnt≥2. Остаётся зависимость от M3R-000 как от **индекса** — по цене чтения, а не по объёму данных |
| промоушен β (Phase 9) | тулинг M3R-020 | условие 6 гейта `phase9_interp` — раунд связности; панель рейтеров недоступна (§3), поэтому измеряет её соло-протокол, и он должен существовать до вердикта фазы (внесено 2026-08-14 при синхронизации спеки Phase 9) |

P2-задачи Track A (M3R-150, M3R-100) не блокируют ничего в Track B по
определению. **Предупреждение исполнителям (в т.ч. агентам):** плоский
список M3R-задач не является последовательностью; выстраивание
искусственных цепочек «сначала весь Track A» — ошибка исполнения, а не
осторожность.

## Track B — Структурный выход

### Phase 9 (M2R-900..902) — интерполяция 3×2 *(закрыта 2026-08-14, β=0)*

> **Вердикт снят** (`docs/eval_reports/eval_2026-08-14_phase9-verdict.md`): грид
> прогнан в двух режимах, must-improve провален всеми шестью плечами. Механизм
> при этом работает — ветвление шага +20%, 7.6% шагов с добавленным кандидатом —
> но до ответа выбор не доходит: его схлопывает отбор кандидатов. Это первое
> прямое доказательство конституционного тезиса на механизме, которому **было**
> что двигать, и оно переводит M3R-011 из «одного из P0» в следующее измерение
> по приоритету: узкое место локализовано в окне отбора, а не в цепи.


Мягкая интерполяция P = (1−β)·P3 + β·P2proj вместо жёсткого бэкоффа;
спека и промпт — `M2R_PHASE9_INTERPOLATION.md`,
`PROMPT_phase9_implementation.md`. Единственный структурный механизм,
работающий на полной мощности уже накопленного корпуса (переходы не
режутся ретенцией); измерено: +26.7% посещений в рабочей зоне при β=0.3.
Ships-disabled (β=0 байт-идентичен), грид β ∈ {0.15, 0.30, 0.50}
**в обоих режимах ctx/noctx** (амендмент: без контекста нет bias,
направляющего расширенные пулы, — риск несвязности выше и меряется
отдельно; провал в noctx при проходе в ctx допускает расщепление ручки
на ctx/noctx-значения решением владельца в вердикте).

### M3R-000 — кумулятивный фразовый индекс *(сделано 2026-08-23; приёмка ждёт редеплоя)*

> **Реализован** (`derive-phrase-index`, миграция 022): таблица
> `chat_phrase_ngrams` с бэкфиллом из `transitions`, пересборка суточным
> пассом, `clear_chat` пополнен. Открыты только пост-деплойные шаги приёмки:
> прохождение суточного пасса по `/stats` и сверка `phrase_census` со свежей
> копией прода (канал свежих копий — `db-snapshot-to-owner`).

> **Задача изменила форму, и это не уточнение, а исправление ошибки.**
> Она была написана как накопитель: индекс копится с нуля, поэтому «каждый
> день без счётчиков = потерянный день данных». Посылка неверна. Контентные
> би/триграммы со всевременными счётчиками **уже лежат в `transitions`** —
> строка `(w1,w2,w3,cnt)` и есть контентная триграмма, сумма группы по `w3` —
> биграмма, а таблица инкрементируется только вверх и стирается лишь `/clear`.
> Замер на прод-копии: 831 фраза cnt≥3, 2465 при cnt≥2
> (`tools/eval/phrase_census.py`). Терять было нечего, ждать — тоже.

Пер-чатовый индекс контентных би/триграмм — **производное представление
цепи**, не второй накопитель. Экстракция — существующий `hot_ngrams.py` как
есть (контентные n-граммы, разрыв на пунктуации — фраза всегда проходимая
смежность). Состав:

- **миграция** создаёт таблицу и **бэкфиллит её из `transitions`** по образцу
  016 (`chat_verbatim_ngrams`); стартовать с нуля значит выбросить
  всевременной корпус;
- **суточный пасс** пересобирает индекс тем же фильтром — единственная точка
  записи. Ловушка per-chat настроек (`reply_pipeline.py:515`) на него не
  распространяется: пересборка ручек не читает вовсе;
- **`clear_chat`** пополняется таблицей, иначе `/clear` её переживёт.

Врезки A (`_absorb_message`) и B (`ReplyPipeline.learn`) **не делаются**:
они покупали свежесть внутри суток ценой записи на горячем learn-пути и
нового пер-чатового кэша — двух ловушек чек-листа §5 сразу, — а читателя,
которому эта свежесть нужна, до M3R-210 не существует, и его порог (cnt≥3)
суточным лагом не двигается. Главное же: два накопителя одного факта
расходятся молча (прецедент — набор мем-регресса из n-грамм поддержки 1 при
пустой hot-таблице, map §3.6), а производный индекс разойтись не может.
Понадобится свежесть — врезка B добавляется поверх отдельным изменением.

Зачем тогда таблица, если данные уже есть: по **цене чтения**. Отбор фраз
прямо из `transitions` стоит 31–80 мс на чат на прод-копии при бюджете p95
150 мс на весь ответ; ключевой доступ дешевле на порядки. Объём ≈ 1.5–1.8 МБ.
Читателей нет (паттерн «схема едет, фича ждёт»). Гейт операционный:
стоимость суточной пересборки и storage в отчёте миграции.

Ко-оккуренсы расстояния 1 **не строить** — уже в `transitions` +
`CollocationsRepo` с полной историей. Широкое окно (±2, ~2 МБ
накопительно) — отдельное решение при дизайне M3R-200, если смежности
не хватит.

### M3R-011 — Structural Escape Gate *(сделано 2026-08-14)*

> **Метрика построена, пороги пре-регистрированы, базлайн снят в двух режимах**
> (`eval_2026-08-14_escape-baseline_{ctx,noctx}.md`, 500×3 сида, прод-копия):
>
> | | ECB по пулу | escape по окну | входов с одной траекторией |
> |---|---|---|---|
> | ctx | 4.455 [4.423, 4.491] | 2.169 [2.115, 2.227] | **36%** |
> | noctx | 4.531 [4.503, 4.559] | 2.941 [2.893, 2.992] | 6% |
>
> **Узкое место измерено: отбор, а не цепь.** Пул одинаково богат в обоих
> режимах (~4.5 траектории из 5), а окно в контекстном режиме вдвое уже. Разница
> между режимами ровно одна — `context_relevance ≡ 0` в noctx, — значит
> пространство схлопывает компонента тематичности скорера.
>
> Отсюда следствие для маршрутов: **тематичность и структурный выбор в текущем
> дизайне конкурируют**. Маршрут обязан производить траектории, различные *и*
> тематичные; «просто больше разных» скорер отбракует, что и показала фаза 9
> (ветвление шага +20%, ECB пула и escape окна — в шуме).
>
> Оговорка о пороге: `window_escape_min: 2.0` зарегистрирован как **среднее**, и
> C0 его формально берёт (2.169) — при том что у 36% входов траектория ровно
> одна. Порог не двигается (пре-регистрация), но форма «доля входов ниже 2»
> честнее среднего и заводится отдельным именем в гейте маршрутов M3R-220.
>
> Базлайн R1 (4.73/4.68 по пулу, 2.4/3.18 кандидата в окне) считался внешним
> харнессом, его JSON в репозиторий не попали — сопоставимость не заявляется,
> база отсчёта теперь эта.


Метрика: число существенно различных траекторий (edge-overlap ниже
порога) **среди кандидатов в окне отбора** (score в пределах margin от
лучшего). Отчёт всегда содержит **пару**: ECB по всему пулу + escape-счёт
по окну — расхождение («разнообразие есть, качественного нет»)
диагностично само по себе. Критерий качества оконно-относительный, не
абсолютный порог: скоры не калиброваны абсолютно, их шкала различается
между режимами (map §1.2). Базлайн C0 — из готовых JSON разведки R1
(в окне сейчас 2.4 кандидата в ctx / 3.18 в noctx; сколько различны —
досчитать). **Главный гейт проекта:** PRE структурно успешен, только если
для входа существует ≥2 существенно различных траекторий в окне отбора —
а не варианты одного почти детерминированного пути. Пороги регистрируются
до первого маршрутного грида. ECB ≥ 4/5 по пулу остаётся страховочным
инвариантом при любых изменениях состава пула.

### M3R-200 — ассоциативный маршрут: пилот → полный

Идея: якоря входа → PMI-окрестность → выбор перспективного
токена/пары → достройка Markov-совместимым хвостом (прямая цепь + реверс
M2R-400). Обобщение доказанного anchoring-принципа с exact-совпадений на
статистическое соседство.

**Пилот (S, после M3R-011/103):** данные — ко-оккуренсы расстояния 1
(`transitions`, полная история) + PMI-граф текущего окна (тонкий: 244
узла — оговаривается в отчёте). Пилот отвечает ровно на четыре вопроса и
**не выносит вердикт о пользе**: (1) архитектурная пригодность — маршрут
строится и сшивается с Markov-хвостом; (2) пространственная — добавляет
ли траектории, которых нет у других маршрутов (escape-счёт);
(3) стоимость — латентность/память/БД; (4) сигнальность — ранний сигнал
по affinity. Лестница фиксирована: пилот → жизнеспособность → накопление
данных → протокольный замер → промоушен; «прототип работает» и «маршрут
полезен» — разные утверждения, смешивать их запрещено гейтом.
**Полный (L):** после решения по широкому окну и его откорма.

### M3R-210 — фразовый маршрут *(L; M3R-000 реализован — после редеплоя блокеров по входу нет)*

> **Планка «≥1000 фраз cnt≥3» снята 2026-08-23 как измеряющая не то.** Она
> формулировалась как условие готовности данных, когда считалось, что фраз 132
> и они копятся. Обе половины неверны: фразы во всевременной цепи, и их 43 229,
> а число, от которого зависит судьба маршрута, — не количество фраз, а доля
> входов, до которых он дотянется. Замер:
> `python -m tools.eval.phrase_census --db db_prod_copy/markov.db --min-count 2 3 5`,
> разбор — `docs/eval_reports/eval_2026-08-23_phrase-index-operational.md`.
>
> | | cnt≥5 | cnt≥3 | cnt≥2 |
> |---|---|---|---|
> | фраз | 281 | 831 | 2465 |
> | самостоятельных (не край прошедшей триграммы) | 253 | 707 | 1826 |
> | **точек прицепа (доля состояний цепи)** | 262 (1.1%) | 744 (**3.1%**) | 1996 (**8.4%**) |
>
> **Порог поддержки становится плечом грида маршрута (2 / 3 / 5), а не
> условием старта.** Он тянет покрытие и качество в разные стороны, и выбирать
> его вслепую нельзя ни в какую сторону: при cnt≥3 маршрут ограничен 3.1%
> входов сверху и рискует провалить coverage, ещё ничего не сгенерировав; при
> cnt≥2 треть добавленных биграмм — края уже прошедших триграмм, то есть
> дубли, которые Escape по edge-overlap за отдельную траекторию не засчитает,
> а сами фразы поддержки 2 стоят в шаге от лотереи поддержки 1 (R4).
>
> Пре-регистрировать для маршрута осмысленно **покрытие входов и escape**, а не
> число строк в таблице. Правка правомерна: «≥1000 фраз» — проза этого
> документа, в `eval_thresholds.yaml` такого порога нет и не было, поэтому
> правило §1.3 о неизменности пре-регистрированных порогов не затрагивается.
>
> Остаётся зависимость от M3R-000 как от **индекса** (цена чтения), не как от
> откорма.

Фраза из кумулятивного индекса вставляется **как единица** (не проход по
рёбрам с единичным счётчиком — R4: это лотерея), сшивка границ
Markov-совместима. Обязательно: полный финализационный конвейер
`_finalize_attempt` (урок seeded) и verbatim-исключение M3R-120 — **последнее
перестало быть формальностью**: вставка корпусной фразы поднимает
`verbatim_ngram_overlap`, поэтому низкий порог поддержки без M3R-120 отдаёт
анти-цитатному штрафу ровно те кандидаты, ради которых порог опускали.
`context_relevance` — союзник маршрута (+0.5…0.7 за релевантную фразу).

### M3R-220 — гейт маршрутов

Каждый маршрут — отдельная ablation-рука со своим гейтом до включения
(атрибуция вклада как в 2.0R). Гейт = Escape-метрика (≥2 различных
качественных траекторий) + affinity_without_copy не ниже лучшей одиночной
конфигурации + copy/repetition не растут + шаблон §4 (coverage,
латентность, два режима) + связность по M3R-020.

Для фразового маршрута сюда добавляется **порог поддержки как плечо**
(2 / 3 / 5, решение 2026-08-23 — см. M3R-210): он двигает покрытие и качество
в разные стороны, поэтому не выбирается заранее, а меряется. Coverage шаблона
§4 для него — не формальность: верхняя оценка доли достижимых входов
измерена и лежит между 1.1% и 8.4% в зависимости от плеча.

### M3R-300 — retrieval-маршрут *(условный, L)*

Ещё один маршрут ансамбля, **не следующая ступень**. Условие запуска:
маршруты подняли Escape-метрику, **но** affinity_without_copy остаётся
ниже целевого — разрыв тематичности закрывается retrieval-композицией
(BM25/инвертированный индекс по накопленному корпусу, конституции не
противоречит). Наследует пол по copy и M3R-120. Плато и здесь = вердикт
«статистический подход исчерпан на этом корпусе», зафиксированный
цифрами, — полноценный результат.

## Success criteria

Против C0 (frozen), по протоколу дока 05 + M3R-011:

- **Structural Escape (главный):** для одного входа PRE даёт ≥2
  существенно различных траекторий в окне отбора, при
  affinity_without_copy не ниже лучшей одиночной конфигурации — иначе PRE
  не считается вышедшим из 99% one-successor, сколько бы кандидатов он ни
  генерировал;
- `context_affinity_without_copy` ↑ значимо (линия C4 → пул → маршруты);
- exact_copy ↓ или не растёт; repetition не растёт;
- ECB-инвариант ≥ 4/5 по пулу при любых изменениях состава пула;
- связность не ниже C0 по соло-протоколу M3R-020; reward-агрегат реакций
  включённой конфигурации ≥ C0 за окно сравнения;
- вклад каждого маршрута атрибутирован (M3R-103); каждая фича заявляет и
  подтверждает целевые F-классы (M3R-021); coverage в каждом гейте;
- гейты в двух режимах ctx/noctx с весом по прод-доле; пустые каналы
  видимы счётчиками; hash-контракт «тёплый==холодный»; перезаморозка
  базлайна только пакетная с записью причин;
- privacy-инварианты 2.0R без изменений; каждая подсистема отключаема;
  каждое изменение поведения — через OpenSpec.
