# План улучшения генерации ответов

## 1. Цель

Цель — повысить связность, естественность и разнообразие ответов
`PepeEdtaBot`, сохранив локальную Markov-архитектуру без внешней LLM и без
передачи содержимого чатов сторонним сервисам.

Предлагаемый подход не требует одномоментной переработки генератора. Изменения
можно внедрять небольшими этапами, сравнивая качество до и после каждого шага.

Основной принцип:

> Генератор должен создавать несколько допустимых вариантов, а отдельный
> компонент — оценивать их и выбирать лучший.

Сейчас значительная часть логики построена вокруг повторных попыток и
последовательного отбрасывания кандидатов. Это защищает от некоторых плохих
ответов, но первый прошедший фильтры вариант не обязательно является лучшим.

## 2. Текущее состояние

Существующий генератор уже имеет важные защитные механизмы:

- variable-order Markov model с порядками 3, 2 и 1;
- fallback на более низкий порядок;
- использование reply-контекста и seed-токенов;
- штраф за повторения;
- регулируемую случайность;
- повторные попытки генерации;
- проверку дословного совпадения с недавними обучающими сообщениями;
- защиту от частого повторения коротких ответов;
- ограничение длины в символах и токенах.

Основная orchestration-логика находится в
`app/handlers/learning.py`. Handler одновременно:

- принимает решение об ответе;
- собирает контекст;
- управляет попытками;
- изменяет параметры между попытками;
- проверяет кандидатов;
- выбирает результат;
- обновляет runtime-состояние.

Это затрудняет развитие алгоритма и тестирование качества независимо от
Telegram.

## 3. Проблемы, которые стоит решать

### 3.1. Первый допустимый кандидат побеждает

Текущая проверка в основном бинарная: кандидат либо принимается, либо
отбрасывается. Два допустимых ответа не сравниваются между собой по качеству.

### 3.2. Контекст влияет на построение, но почти не оценивается после генерации

Seed и context bias могут направить цепь, однако нет итоговой оценки того,
насколько получившийся ответ связан с исходным сообщением.

### 3.3. Нет единого объяснения качества кандидата

Проверки разбросаны между handler и `markov.py`. Сложно ответить, почему
конкретный вариант был выбран или отклонён.

### 3.4. Качество изменений оценивается преимущественно вручную

Unit-тесты хорошо защищают поведение и крайние случаи, но отсутствует
стабильный offline-набор сценариев для сравнения качества двух версий
генератора.

### 3.5. Генерация тесно связана с Telegram-handler

Это увеличивает размер handler, затрудняет повторное использование и мешает
тестировать генерацию как отдельный бизнес-процесс.

## 4. Предлагаемая архитектура

Предлагается выделить отдельный `ResponseGenerator`, отвечающий за полный цикл
подготовки ответа.

```text
Telegram handler
    |
    | GenerationRequest
    v
ResponseGenerator
    |
    +-- CandidateGenerator
    |       |
    |       +-- MarkovGenerator
    |
    +-- CandidateValidator
    |
    +-- CandidateScorer
    |
    +-- CandidateSelector
    |
    v
GenerationResult
```

Рекомендуемое распределение ответственности:

- `learning.py` — Telegram-ввод, решение о необходимости ответа и отправка;
- `ResponseGenerator` — управление попытками и выбор результата;
- `MarkovGenerator` — построение одного кандидата;
- `CandidateValidator` — обязательные запреты;
- `CandidateScorer` — сравнительная оценка допустимых кандидатов;
- `GenerationResult` — результат и безопасная диагностическая информация.

Пример внутренних моделей:

```python
@dataclass(frozen=True, slots=True)
class GenerationRequest:
    chat_id: int
    context_tokens: tuple[str, ...]
    max_chars: int
    max_tokens: int


@dataclass(frozen=True, slots=True)
class CandidateEvaluation:
    text: str
    score: float
    rejection_reason: str | None
    metrics: dict[str, float]


@dataclass(frozen=True, slots=True)
class GenerationResult:
    text: str | None
    attempts: int
    accepted_candidates: int
    rejection_counts: dict[str, int]
```

Имена и точные поля следует уточнить при реализации. В публичные структуры не
нужно помещать исходный текст пользователя или другие чувствительные данные.

## 5. Candidate generation

Вместо остановки на первом прошедшем фильтры варианте предлагается:

1. создать ограниченное число кандидатов;
2. применить к каждому обязательные проверки;
3. оценить прошедшие варианты;
4. выбрать вариант с наибольшим score;
5. использовать fallback-ответ только при отсутствии допустимых кандидатов.

Начальная конфигурация:

- 6 кандидатов для обычного вероятностного ответа;
- 8 кандидатов при прямом обращении к боту;
- ограниченный общий budget попыток;
- часть попыток с контекстом;
- часть попыток без контекста;
- постепенное увеличение randomness только в пределах budget.

Числа должны стать конфигурируемыми после появления offline-метрик. Сразу
выносить все коэффициенты в `/set` не рекомендуется: это усложнит интерфейс до
понимания реального влияния параметров.

## 6. Обязательная валидация кандидатов

Validator должен отвечать только на вопрос: можно ли вообще отправлять этот
кандидат.

Причины отклонения рекомендуется оформить как стабильные идентификаторы:

- `empty`;
- `over_limit`;
- `verbatim_copy`;
- `recent_short_reply`;
- `repetition_loop`;
- `low_diversity`;
- `bad_start`;
- `bad_ending`;
- `context_copy`.

Обязательные проверки:

- пустой или пробельный результат;
- превышение лимитов Telegram и внутренних лимитов;
- дословное совпадение с обучающим сообщением;
- почти дословное повторение reply-контекста;
- зацикливание токенов;
- чрезмерное повторение одного слова или короткой последовательности;
- повтор недавно отправленного короткого ответа;
- окончание на явно незавершённой конструкции.

Validator не должен самостоятельно выбирать лучший ответ. Мягкие недостатки
следует учитывать в score, иначе слишком строгая фильтрация снова приведёт к
множеству пустых результатов.

## 7. Scoring кандидатов

Начальная формула может быть простой и объяснимой:

```text
score =
    context_relevance
  + lexical_diversity
  + completion_quality
  + natural_length
  + model_confidence
  - repetition_penalty
  - context_copy_penalty
  - awkward_boundary_penalty
```

### 7.1. Context relevance

Без embeddings и внешней модели можно использовать:

- пересечение значимых токенов с контекстом;
- совпадение биграмм;
- близость стартовых токенов к reply-контексту;
- присутствие контекстных слов не только в начале, но и внутри ответа.

Нужно исключать частые служебные слова из положительной оценки, иначе ответы
будут получать высокий score за совпадения вроде «и», «это», «в».

### 7.2. Lexical diversity

Возможные признаки:

- отношение уникальных токенов к общему количеству;
- доля самого частого токена;
- число повторяющихся биграмм и триграмм;
- длина максимальной повторяющейся последовательности.

Для очень коротких ответов эти метрики должны иметь отдельные пороги.

### 7.3. Completion quality

Кандидат получает бонус, если:

- заканчивается допустимой пунктуацией;
- последняя конструкция выглядит завершённой;
- не обрывается на предлоге, союзе, частице или открывающей скобке;
- кавычки и скобки сбалансированы.

### 7.4. Natural length

Не стоит всегда предпочитать самый длинный ответ. Полезнее задавать мягкий
целевой диапазон:

- короткий ответ допустим для короткого обращения;
- средняя длина предпочтительна для обычного контекста;
- слишком длинные варианты получают штраф ещё до жёсткого лимита.

### 7.5. Model confidence

Markov-генератор может возвращать вспомогательные признаки:

- сколько переходов было сделано на основном порядке;
- сколько раз использовался backoff;
- среднюю частоту выбранных переходов;
- число аварийных или случайных fallback-переходов.

Кандидат, построенный преимущественно на устойчивых переходах высокого порядка,
обычно должен получать преимущество, но не настолько сильное, чтобы генератор
всегда воспроизводил самые частые фразы.

## 8. Улучшение начала и окончания фраз

Отдельно стоит улучшить модель границ предложения.

### Минимальный вариант

- хранить признаки начала и конца сообщения;
- не завершать ответ на наборе запрещённых токенов;
- сделать ещё несколько шагов генерации при слабом окончании;
- обрезать только до последней безопасной границы предложения.

### Расширенный вариант

Добавить специальные токены:

- `<BOS>` — начало последовательности;
- `<EOS>` — конец последовательности.

Они позволят модели учиться не только переходам между словами, но и вероятности
естественного завершения. Такое изменение затрагивает схему данных и требует
миграционного плана либо перестроения модели, поэтому его разумно выполнять
после внедрения scoring и offline evaluation.

## 9. Работа с контекстом

Контекст лучше использовать двумя способами:

1. направлять часть кандидатов через seed и context bias;
2. оценивать итоговую релевантность всех кандидатов.

Рекомендуемая стратегия:

- первые кандидаты генерируются с reply-контекстом;
- несколько кандидатов — с ослабленным context bias;
- последние кандидаты — без seed, чтобы избежать тупика;
- итоговый scorer сравнивает их по одним правилам.

Это позволит выбирать связный ответ, не заставляя каждую фразу начинаться с
буквального продолжения пользовательского сообщения.

## 10. Обучающий корпус

Качество ответа ограничено качеством входных сообщений. До записи в модель
полезно классифицировать сообщения.

Не рекомендуется обучаться на:

- Telegram-командах;
- сообщениях, состоящих преимущественно из URL;
- автоматически сгенерированных уведомлениях;
- длинных последовательностях одинаковых символов;
- сообщениях с недостаточной долей содержательных токенов;
- потенциальных секретах и токенах доступа;
- номерах телефонов и email, если они не нужны продукту.

Важно не превращать фильтр в непрозрачную систему цензуры. Для каждого
исключения должна существовать конкретная privacy- или quality-причина и тест.

## 11. Offline evaluation

До настройки весов scoring нужен воспроизводимый evaluation harness.

Предлагаемая структура:

```text
tests/
    generation_cases/
        basic_contexts.json
        short_replies.json
        repetition_cases.json
    test_response_generator.py

tools/
    evaluate_generation.py
```

Evaluation-набор не должен содержать реальные приватные сообщения. Лучше
использовать синтетические или вручную обезличенные сценарии.

### Автоматические метрики

- `empty_result_rate`;
- `verbatim_copy_rate`;
- `context_copy_rate`;
- `repetition_rejection_rate`;
- `average_unique_token_ratio`;
- `bad_ending_rate`;
- `average_attempts`;
- `average_accepted_candidates`;
- `context_token_overlap`;
- `generation_latency_ms`.

### Ручная оценка

Для контрольного набора полезна шкала 1–5:

- связность;
- уместность;
- естественность;
- разнообразие;
- юмористическая ценность;
- отсутствие явной копии.

Ручной score не должен быть CI-gate. Его назначение — сравнивать алгоритмы и
обнаруживать случаи, где автоматические метрики дают ложное ощущение прогресса.

## 12. Детерминированность

Для воспроизводимости следует отказаться от прямого использования глобального
`random` внутри генерационного контура.

Предпочтительный вариант:

- передавать объект `random.Random`;
- в production создавать его без фиксированного seed;
- в тестах использовать известный seed;
- сохранять только безопасный идентификатор seed в debug-диагностике, если это
  действительно нужно.

Это позволит:

- воспроизводить плохие ответы;
- сравнивать две версии алгоритма на одинаковой случайной последовательности;
- писать устойчивые regression-тесты;
- проводить корректные benchmark-сравнения.

## 13. Наблюдаемость без утечки текста

Нужно собирать агрегированные технические показатели без логирования исходного
сообщения или сгенерированного ответа.

Пример:

```text
generation chat=<masked> attempts=6 accepted=3 selected_score=4.71
rejections=empty:1,repetition_loop:1,verbatim_copy:1 latency_ms=24
```

Не следует логировать:

- raw `chat_id` и `user_id`;
- текст пользователя;
- полный reply-контекст;
- сгенерированный ответ;
- токены, по которым можно восстановить содержание разговора.

## 14. Производительность

Генерация нескольких кандидатов увеличит число обращений к SQLite и кэшу.
Перед повышением candidate budget необходимо измерить:

- latency одного кандидата;
- число SQL-запросов;
- hit rate кэшей переходов;
- время scoring;
- конкурентное поведение в одном и разных чатах.

Возможные оптимизации:

- переиспользовать загруженные переходы между кандидатами;
- ограничить одновременную генерацию per-chat lock;
- кэшировать безопасные агрегаты модели;
- задать общий time budget генерации;
- прекращать поиск раньше, если найден кандидат с достаточно высоким score.

Оптимизация не должна менять семантику без тестов. Для небольшого группового
бота предсказуемость важнее преждевременного усложнения.

## 15. Этапы реализации

### Этап 1 — архитектурное выделение без изменения поведения

Создать `ResponseGenerator` и перенести в него текущий цикл попыток.

Результат:

- Telegram-handler становится тоньше;
- поведение остаётся прежним;
- появляются отдельные unit-тесты orchestration.

Критерий готовности:

- существующие тесты проходят;
- набор ответов при фиксированном RNG эквивалентен старому пути;
- handler не управляет внутренними попытками Markov-генерации.

### Этап 2 — детерминированный RNG и диагностические причины

Добавить injected RNG и стабильные rejection reasons.

Результат:

- воспроизводимые regression-тесты;
- измеримость текущего алгоритма до изменения выбора.

### Этап 3 — несколько кандидатов и базовый scoring

Реализовать:

- сбор нескольких допустимых кандидатов;
- context relevance;
- lexical diversity;
- repetition penalty;
- natural length;
- выбор максимального score.

На этом этапе не менять схему БД.

### Этап 4 — offline evaluation harness

Добавить синтетический корпус, CLI-отчёт и baseline текущей версии.

Критерий готовности:

- отчёт воспроизводится по фиксированному seed;
- можно сравнить baseline и новую стратегию;
- latency и причины отказов входят в отчёт.

### Этап 5 — границы предложений

Сначала внедрить правила плохого начала/окончания. После оценки эффекта принять
решение о `<BOS>/<EOS>` и возможной миграции модели.

### Этап 6 — улучшение корпуса и privacy

Добавить фильтры чувствительных данных и пересмотреть необходимость хранения
`normalized_text`. Предпочтительный долгосрочный вариант — хранить ограниченное
окно keyed-хэшей для deduplication вместо near-verbatim текста.

### Этап 7 — профили генерации

После стабилизации метрик можно добавить профили:

- `conservative`;
- `balanced`;
- `chaotic`.

Профиль должен выбирать заранее протестированный набор параметров, а не
открывать пользователю десятки внутренних коэффициентов.

## 17. Что не рекомендуется делать сразу

- Подключать внешнюю LLM без отдельного privacy-решения.
- Переписывать весь `markov.py` одним большим изменением.
- Добавлять большое число настраиваемых коэффициентов в `/set`.
- Использовать только token overlap как показатель уместности.
- Делать строгие фильтры, из-за которых бот часто перестаёт отвечать.
- Оптимизировать SQL и кэширование до появления измерений.
- Использовать реальные приватные сообщения как открытые test fixtures.

## 18. Ожидаемый эффект

После этапов 1–4 ожидается:

- меньше случайных, но формально допустимых ответов;
- меньше повторов и обрывов;
- более заметная связь с reply-контекстом;
