# Операционный runbook

Процедуры для долгоживущего деплоя `PepeEdtaBot`: что делать руками и в каком
порядке. Устройство системы — [ARCHITECTURE.md](ARCHITECTURE.md), параметры —
[`.env.example`](../.env.example).

Бот работает через long polling к Telegram Bot API, хранит данные в SQLite
(WAL), пишет логи в stdout, разворачивается через Docker/Compose. HTTP-эндпоинта,
эндпоинта метрик и встроенного планировщика бэкапов нет.

## Логи

Приложение пишет в stdout; ротацию настраивает окружение вокруг контейнера.

Минимум: хранить хотя бы 3 ротированных файла, ограничить размер одного файла,
следить за счётчиком рестартов и всплесками ошибок отдельно от файлов логов.

Для стандартного docker-драйвера `json-file` ротация задаётся на хосте (это
настройка демона, не файл репозитория):

```json
{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "10m",
    "max-file": "3"
  }
}
```

Если платформа ротирует stdout сама (journald и подобные) — проверьте, что
retention конечен, логи ищутся по имени контейнера, а события рестарта и stderr
хранятся вместе со stdout.

`chat_id` в логах маскирован; расшифровать его обратно нельзя, и это
намеренно — сопоставлять записи можно только по маске.

## Обслуживание WAL

Включён `PRAGMA journal_mode=WAL`, поэтому одна логическая база — это три файла:
`data/markov.db`, `data/markov.db-wal`, `data/markov.db-shm`.

Ручной checkpoint нужен, когда `-wal` неожиданно вырос, перед «холодным»
бэкапом или если после падения размер WAL остаётся большим:

```bash
python -c "import sqlite3; conn = sqlite3.connect('data/markov.db'); print(conn.execute('PRAGMA wal_checkpoint(TRUNCATE);').fetchall()); conn.close()"
```

Ожидаемый результат — одна строка от `wal_checkpoint`; после успешного truncate
WAL заметно сжимается или исчезает на простое. Для самого консервативного
сценария остановите бота перед командой.

## Бэкапы

**Холодная копия** (когда бота можно остановить): остановить → скопировать
`data/markov.db` и, если есть, `-wal`/`-shm` → запустить снова. После чистой
остановки с checkpoint'ом обычно остаётся только `markov.db`, но процедура
должна переживать и наличие WAL/SHM.

**Онлайн-бэкап** (без остановки):

```bash
python -c "import sqlite3; src = sqlite3.connect('data/markov.db'); dst = sqlite3.connect('data/markov.backup.sqlite'); src.backup(dst); dst.close(); src.close()"
```

После онлайн-бэкапа полезно прогнать checkpoint, чтобы WAL не рос.

**Бэкап не считается сделанным, пока не проверен:**

```bash
python -c "import sqlite3; conn = sqlite3.connect('data/markov.backup.sqlite'); print(conn.execute('PRAGMA integrity_check;').fetchone()); conn.close()"
```

Ожидаемый результат: `('ok',)`.

## Восстановление

Только при остановленном боте:

1. Остановить контейнер/процесс.
2. Убрать текущие `data/markov.db`, `data/markov.db-wal`, `data/markov.db-shm`.
3. Положить выбранный бэкап как `data/markov.db`.
4. Проверить, что владелец файла — рантайм-пользователь.
5. Запустить бота.
6. Посмотреть логи старта, проверить `/ping` и `/stats`.

Если бэкап — одиночный SQLite-файл, не кладите рядом устаревшие `-wal`/`-shm`.

## Проверки после рестарта

Контейнер/процесс запущен; в логах нормальный старт без ошибок миграций;
`/ping` отвечает; `/stats` работает в группе; `data/markov.db` доступен на
запись рантайм-пользователю.

Настройки, менявшиеся через `/set`, рестарт не переживают: они живут в памяти
процесса. После рестарта действуют значения из `.env`.

## Секреты

`PIVO_HMAC_SECRET` и `PIVO_ENCRYPTION_SECRET` обязаны быть не короче
32 символов и различаться между собой. Более короткий секрет **останавливает
старт** с явной ошибкой: это осознанный выбор — молчаливый запуск со слабым
ключом и есть та ситуация, ради которой порог введён. Сгенерировать:

```bash
python -c "import secrets; print(secrets.token_urlsafe(32))"
```

Смена `PIVO_ENCRYPTION_SECRET` делает нечитаемыми уже сохранённые подписки
`/pivo`; смена `PIVO_HMAC_SECRET` дополнительно обнуляет статус
«завсегдатаев» и разрывает сопоставимость масок `chat_id` в логах через
границу смены. Ни то, ни другое не авария, но и не откатывается.

Схема вывода ключа шифрования сменилась 2026-08-06
(см. [ARCHITECTURE.md](ARCHITECTURE.md#приватность-и-безопасность)). Миграции
данных не требуется: чтение идёт набором ключей, прежний остаётся читающим, а
строки переходят на новый при очередной перезаписи профиля подписчика
(`/pivo_on` или первое сообщение участника за сутки).

## Retention данных

Что и как долго хранится, описано в
[ARCHITECTURE.md](ARCHITECTURE.md#модель-данных); здесь — что с этим делать
оператору.

Чистится автоматически: окно `messages` (после каждой вставки), суточные квоты
`/pivo` (на старте), «личностные» таблицы (затухание на старте и примерно раз в
сутки). Не чистится ничего из агрегированной модели Маркова — она и есть вся
выученная история чата; сбросить её можно только `/clear confirm` в самом чате.

`MESSAGES_RETENTION_PER_CHAT` должно быть не меньше `TEXT_CACHE_MAX_MESSAGES`,
иначе старт падает: гейт дословных копий читал бы больше сообщений, чем
хранится.

Удаление строк само по себе не уменьшает файл БД. Чтобы вернуть страницы
файловой системе, прогоните `VACUUM` в окно обслуживания; для сжатия WAL может
дополнительно потребоваться `PRAGMA wal_checkpoint(TRUNCATE)`.

Размер по таблицам:

```bash
python -c "
import sqlite3
conn = sqlite3.connect('data/markov.db')
rows = conn.execute('SELECT name, SUM(pgsize) FROM dbstat GROUP BY name ORDER BY 2 DESC').fetchall()
for name, size in rows:
    print(f'{name}: {size // 1024} KB')
conn.close()
"
```

**Расписание для небольшой активной группы** (до ~10 человек): ежемесячно —
проверить размер файла БД и при необходимости сделать checkpoint;
ежеквартально — посмотреть размер по таблицам и запланировать `VACUUM`.

## Что на самом деле проверяет HEALTHCHECK

Docker `HEALTHCHECK` проверяет, что Python стартует и файл БД читается. Он
**не** доказывает, что polling жив, что записи в SQLite проходят и что event
loop двигается. Это минимальная smoke-проба, а не сигнал готовности.
