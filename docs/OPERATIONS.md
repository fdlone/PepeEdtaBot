# Операционный runbook

Процедуры для долгоживущего деплоя `PepeEdtaBot`: что делать руками и в каком
порядке. Устройство системы — [ARCHITECTURE.md](ARCHITECTURE.md), параметры —
[`.env.example`](../.env.example).

Бот работает через long polling к Telegram Bot API, хранит данные в SQLite
(WAL), пишет логи в stdout, разворачивается через Docker/Compose.
HTTP-эндпоинта и эндпоинта метрик нет. Планировщика бэкапов нет, но автоснимок
БД делается на каждом старте процесса и уходит владельцу в личку (см. §Бэкапы).

## Логи

Приложение пишет в stdout; ротацию настраивает окружение вокруг контейнера.

Минимум: хранить хотя бы 3 ротированных файла, ограничить размер одного файла,
следить за счётчиком рестартов и всплесками ошибок отдельно от файлов логов.

Для стандартного docker-драйвера `json-file` ротация задаётся на хосте (это
настройка демона, не файл репозитория):

```json
{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "10m",
    "max-file": "3"
  }
}
```

Если платформа ротирует stdout сама (journald и подобные) — проверьте, что
retention конечен, логи ищутся по имени контейнера, а события рестарта и stderr
хранятся вместе со stdout.

`chat_id` в логах маскирован; расшифровать его обратно нельзя, и это
намеренно — сопоставлять записи можно только по маске.

## Обслуживание WAL

Включён `PRAGMA journal_mode=WAL`, поэтому одна логическая база — это три файла:
`data/markov.db`, `data/markov.db-wal`, `data/markov.db-shm`.

Ручной checkpoint нужен, когда `-wal` неожиданно вырос, перед «холодным»
бэкапом или если после падения размер WAL остаётся большим:

```bash
python -c "import sqlite3; conn = sqlite3.connect('data/markov.db'); print(conn.execute('PRAGMA wal_checkpoint(TRUNCATE);').fetchall()); conn.close()"
```

Ожидаемый результат — одна строка от `wal_checkpoint`; после успешного truncate
WAL заметно сжимается или исчезает на простое.

## Бэкапы

**Снимок через бота** (основной путь; хост трогать не нужно): на каждом старте
процесса, до применения миграций, бот снимает консистентный снимок
(`VACUUM INTO`), сжимает gzip и шлёт документом в личку `OWNER_ID` —
`markov-<UTC-метка>.db.gz`. По запросу то же делает owner-only команда
`/db_snapshot` в личке. Выключатель автоснимка — `DB_SNAPSHOT_TO_OWNER=false`;
без `OWNER_ID` снимок не снимается. Отказ доставки (личный чат с ботом не
открыт, сеть) не ломает запуск — в логе `db snapshot ... failed`. Файл крупнее
50 МБ (лимит Bot API) заменяется текстовым предупреждением. Снимок пишется во
временный каталог — на тесном диске это разовый пик размером с БД.

**Холодная копия** (когда бота можно остановить): остановить → скопировать
`data/markov.db` и, если есть, `-wal`/`-shm` → запустить снова. После чистой
остановки с checkpoint'ом обычно остаётся только `markov.db`, но процедура
должна переживать и наличие WAL/SHM.

**Онлайн-бэкап с хоста** (без остановки, если снимок через бота недоступен):

```bash
python -c "import sqlite3; conn = sqlite3.connect('data/markov.db'); conn.execute(\"VACUUM INTO 'data/markov.backup.sqlite'\"); conn.close()"
```

`VACUUM INTO` отдаёт однофайловый консистентный снимок — checkpoint и возня с
`-wal`/`-shm` не нужны.

**Бэкап не считается сделанным, пока не проверен:**

```bash
python -c "import sqlite3; conn = sqlite3.connect('data/markov.backup.sqlite'); print(conn.execute('PRAGMA integrity_check;').fetchone()); conn.close()"
```

Ожидаемый результат: `('ok',)`.

## Восстановление

Только при остановленном боте:

1. Остановить контейнер/процесс.
2. Убрать текущие `data/markov.db`, `data/markov.db-wal`, `data/markov.db-shm`.
3. Положить выбранный бэкап как `data/markov.db`.
4. Проверить, что владелец файла — рантайм-пользователь.
5. Запустить бота.
6. Посмотреть логи старта, проверить `/ping` и `/stats`. При включённом
   автоснимке в личку владельца должен прийти `markov-<UTC>.db.gz`; его
   отсутствие — самостоятельный сигнал (искать в логе `db snapshot`).

Если бэкап — одиночный SQLite-файл, не кладите рядом устаревшие `-wal`/`-shm`.

## Проверки после рестарта

### Живость

Контейнер/процесс запущен; в логах нормальный старт без ошибок миграций;
`/ping` отвечает; `/stats` работает в группе; `data/markov.db` доступен на
запись рантайм-пользователю.

**Ответ на команду не доказывает, что генерация работает.** Команды отвечают
заготовленным текстом, минуя Markov-генератор целиком. Единственная
проверка генерации — **упомянуть бота** (упоминание отвечает детерминированно,
а не по ролю `reply_probability`) и убедиться, что после этого в `/stats`
появилась строка «генераций с рестарта» с ненулевым числом. Один ответ даёт
примерно `CANDIDATE_TARGET` генераций: счётчик считает кандидатов, а не ответы.

### Верификация после деплоя

Снимать сразу, пока окно наблюдения не началось:

- `markov_token_df` пишется и `n_docs` растёт — по БД (первый раз проверено
  24.08.2026, M3R-001); если df **не** пишется — чинить learn-путь отдельным
  изменением;
- телеметрия шага отдаёт числа: в `/stats` есть строки энтропии/ветвления и
  доли режима;
- «кэш распределений» в норме (на первых единицах генераций число ещё шум —
  читать после накопления).

### Счётчики `/stats` живут в памяти процесса

Всё, что печатается ниже «объём модели» и «коллокации», — счётчики
`GenerationTelemetry` на инстансе генератора. **Любой рестарт их обнуляет и
открывает окно накопления заново.** Практические следствия:

- **перед плановым редеплоем снять `/stats` и записать вывод** — иначе
  накопленное теряется безвозвратно (например, был ли у ответа контекст, из
  БД не восстановить);
- накопление **в БД** (`markov_token_df`, коллокации, горячие n-граммы,
  фразовый индекс, метка обслуживания) рестарт переживает — путать эти два
  вида накопления нельзя;
- гейт, объявивший `requires_both_modes`, взвешивается по прод-доле режима
  (`ctx_generation_share`) — окно после редеплоя даёт вход вердикта; суток
  активности достаточно.

Строка блока телеметрии генерации присутствует в `/stats` только тогда, когда
её знаменатель ненулевой (строки вне блока — темп чата, воронка причуд,
стоимость мемо-пасса — печатаются по своим правилам). Отсутствие строки
означает «нечего показать» **или** «этого счётчика нет в выкаченной сборке».
Различать — по первой строке `/stats`:

```
сборка: 2026-08-23T22:00:26+03:00
```

Это время сборки образа (`RUN date -Is > /app/BUILD_AT` в `Dockerfile`; штамп
обновляется тогда и только тогда, когда менялось содержимое `main.py` или
`app/`). Проверка «есть ли в этой сборке коммит X» — одна сверка:

```bash
git log -1 --format=%cI <sha>   # когда коммит попал в историю
```

Штамп новее — коммит в сборке есть. Варианты строки:

- `сборка: <дата>` — сверить с `git log`;
- `сборка: unknown` — запуск не из образа (`python main.py` на хосте);
- строки нет вовсе — образ собран до появления штампа (2026-08-24).

Штамп — время, а не ревизия (`.git` в контекст сборки не уходит); двух
коммитов одной минуты он не различит.

### Настройки

Настройки, менявшиеся через `/set`, рестарт не переживают: они живут в памяти
процесса (пер-чатовым оверлеем; чат, о котором бот давно не слышал, возвращается
к глобальным значениям вместе с остальным своим состоянием). После рестарта
действуют значения из `.env`.

## Секреты и другие причины не стартовать

`PIVO_HMAC_SECRET` и `PIVO_ENCRYPTION_SECRET` обязаны быть не короче
32 символов и различаться между собой; более короткий секрет останавливает
старт с явной ошибкой. Кроме секретов запуск роняют: опечатка в
`CHAT_TIMEZONE` (неизвестное имя IANA-зоны), невалидное булево в
`DB_SNAPSHOT_TO_OWNER` / `GEN_TRACE_LOG` и
`MESSAGES_RETENTION_PER_CHAT < TEXT_CACHE_MAX_MESSAGES`. Сгенерировать секрет:

```bash
python -c "import secrets; print(secrets.token_urlsafe(32))"
```

Смена `PIVO_ENCRYPTION_SECRET` делает нечитаемыми уже сохранённые подписки
`/pivo`; смена `PIVO_HMAC_SECRET` дополнительно обнуляет статус
«завсегдатаев» и разрывает сопоставимость масок `chat_id` в логах через
границу смены. Ни то, ни другое не авария, но и не откатывается.

Схема вывода ключа шифрования сменилась 2026-08-06
(см. [ARCHITECTURE.md](ARCHITECTURE.md#приватность-и-безопасность)). Миграции
данных не требуется: чтение идёт набором ключей, прежний остаётся читающим, а
строки переходят на новый при очередной перезаписи профиля подписчика
(`/pivo_on` или первое сообщение участника за сутки).

## Retention данных

Что и как долго хранится, описано в
[ARCHITECTURE.md](ARCHITECTURE.md#модель-данных); здесь — что с этим делать
оператору.

Чистится автоматически: окно `messages` (после каждой вставки), суточные квоты
`/pivo` (на старте), «личностные» таблицы (затухание на старте и раз в сутки —
каденция считается от метки `maintenance_meta` и переживает рестарт). На том же
суточном такте переписываются целиком реестр коллокаций и фразовый индекс —
оба производные, потерь при перезаписи нет. Не чистится ничего из
агрегированной модели Маркова — она и есть вся выученная история чата;
сбросить её можно только `/clear confirm` в самом чате.

`MESSAGES_RETENTION_PER_CHAT` должно быть не меньше `TEXT_CACHE_MAX_MESSAGES`,
иначе старт падает: гейт дословных копий читал бы больше сообщений, чем
хранится.

Удаление строк само по себе не уменьшает файл БД. Чтобы вернуть страницы
файловой системе, прогоните `VACUUM` в окно обслуживания; для сжатия WAL может
дополнительно потребоваться `PRAGMA wal_checkpoint(TRUNCATE)`.

Размер по таблицам:

```bash
python -c "
import sqlite3
conn = sqlite3.connect('data/markov.db')
rows = conn.execute('SELECT name, SUM(pgsize) FROM dbstat GROUP BY name ORDER BY 2 DESC').fetchall()
for name, size in rows:
    print(f'{name}: {size // 1024} KB')
conn.close()
"
```

**Расписание для небольшой активной группы** (до ~10 человек): ежемесячно —
проверить размер файла БД и при необходимости сделать checkpoint;
ежеквартально — посмотреть размер по таблицам и запланировать `VACUUM`.

## Что на самом деле проверяет HEALTHCHECK

Docker `HEALTHCHECK` проверяет, что Python стартует и файл БД читается. Он
**не** доказывает, что polling жив, что записи в SQLite проходят и что event
loop двигается. Это минимальная smoke-проба, а не сигнал готовности.
