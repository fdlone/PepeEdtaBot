# Поведенческая карта механики генерации

Что система **делает** на текущих дефолтах — в отличие от того, из чего она
состоит ([ARCHITECTURE.md](ARCHITECTURE.md)) и как устроен путь по функциям
([GENERATION_PIPELINE.md](GENERATION_PIPELINE.md)). Карта дополняет их, не
дублирует: здесь статусы ручек, обходные ветки, тихие деградации и расхождения
между тем, что меряет eval, и тем, что происходит в проде.

Дата: 2026-08-13. Снимок: `db_prod_copy/markov.db` (2026-07-13), боевой чат
(здесь и далее — синтетический `-1001234567890`, `tests/test_no_real_chat_ids.py`):
1000 удержанных сообщений, объём модели 32223/27550,
`transitions3` 27 237 строк, `starts3` 4 403, `chat_verbatim_ngrams` 19 578.

| метка | значит |
|---|---|

**Это разведка, а не протокольный прогон.** Один снимок, один сид (42), 300

интервалы. Числа годятся для «так работает / так не работает», не годятся для
вердикта фазы.

**Как измерено.** Код проекта не изменён ни в одном файле. Харнесс
`tools/sweeps/genmap_2026-08-13.py` подменяет семь хуков `gen_trace_log.*` и

`_mutated_variant`, `_append_seeded_candidates`) — обёртка вызывает оригинал и
записывает, что он вернул. Приём тот же, что у `tools/eval/run.py` и у ревью
`REVIEW_2026-08-13.md`. `reply_flavor_strength` и `emoji_append_chance`
занулены во всех армах: оба слоя работают после отбора и на пул не влияют.

**Армы.**

| арм | что моделирует |
|---|---|
| `ctx` | контекст = промпт — ровно то, что делает `tools/eval/run.py` |
| `noctx` | контекст пуст — **непрошеный ответ на не-реплай в проде** |
| `live` / `livectx` | то же + тёплая анти-повторная память (`recent_replies`) |
| `seeded` | `ctx` + `markov_seeded_candidate_ratio=0.3` |
| `hotseed` | `noctx` + L1-затравка из горячей n-граммы на каждой генерации |

## 1.2 Главная развилка: есть контекст или нет — это два разных бота

`extract_context_tokens` возвращает пустой список, если
`reply_context_only_for_replies=true` (дефолт) и сообщение не является реплаем
`[код reply_pipeline.py:174]`. Прямое обращение переопределяет это
`[код reply_pipeline.py:629]`. Значит **непрошеный ответ на сообщение, которое
не является реплаем, идёт вообще без контекста**.

Какая доля прод-ответов приходится на этот режим — **не измерено**: для этого
нужен счётчик «ответ с контекстом / без» на живом проде, которого нет (§3.1).
Ниже показано только то, чем два режима отличаются.

`tools/eval/run.py` передаёт `context_tokens=tokenize(prompt)` **всегда**
`[код tools/eval/run.py:236]`, минуя `_context_tokens` целиком. То есть весь
протокол измеряет только режим с контекстом.

Что меняется при пустом контексте `[замер 300 генераций × 2 арма, сид 42]`:

| метрика | `ctx` | `noctx` |
|---|---|---|
| `context_relevance`: среднее / размах в пуле | 0.191 / 0.498 | **0.000 / 0.000** |
| доля пулов, где `context_relevance` — решающая компонента | **0.463** | **0.000** |
| доля пулов, где решает `natural_length` | 0.307 | **0.450** |
| доля пулов, где решает `verbatim_penalty` | 0.130 | **0.317** |
| доля пулов, где решает `completion_quality` | 0.057 | 0.170 |
| кандидатов в окне отбора 0.3 | 2.40 | **3.18** |
| побеждает лучший по скору | 0.697 | **0.627** |
| пулов, где **весь** пул в окне (отбор = лотерея) | 0.080 | **0.120** |
| попыток основного цикла | 5.28 | 4.50 |

По категориям промптов доля пулов, где решает тематичность
`[замер, арм ctx]`: meme-bait 0.61, topical 0.52, generic 0.47,
short-degenerate 0.25. В `noctx` — 0.00 во всех четырёх.

**Вывод.** Без контекста скорер перестаёт быть оценщиком тематичности и
становится «фильтром длины и анти-цитаты»: `idf_context_relevance` возвращает
0 при пустом контексте `[код candidate_scorer.py:284]`, и это ноль для всех
кандидатов сразу, то есть компонента не различает их вовсе. Отбор становится
заметно ближе к жребию (окно шире, лучший побеждает реже). Одновременно
выключаются: контекстный старт, `context_start_affinity`, `context_jump_boost`,
`context_anchor_splice_probability`, `reply_context_bias`, оба контекстных
реджекта цепи. Это не деградация — это **штатный и, вероятно, преобладающий
режим, ни разу не измеренный протоколом**.

## 1.6 Порядок потребления RNG

Один `random.Random` на генерацию `[код response_generator.py:715]`. В проде он
создаётся **несидированным**: `rng=random.Random()` `[код reply_pipeline.py:420]`.
Воспроизводимость существует только через вход харнесса/eval, который передаёт
свой сидированный генератор.

Порядок внутри генерации:

1. `sample_length_mode` — ровно один `rng.choices` `[код response_generator.py:419]`.
2. Для каждой попытки (`_generate_text_once`):
   1. `_pick_seed_start` — RNG только если seed попал в 2-граммный старт;
   2. `rng.random()` на `use_contextual_start` — **безусловно** `[код markov.py:2392]`;
   3. контекстный каскад: `_roll_exploration` (1 или 3 draw'а) + взвешенный выбор; для 2-граммного тира ещё `weighted_next_choice`;
   4. `rng.random()` на сегментацию якоря — **только при ненулевой ручке** (короткое замыкание проверяет ручку до ролла) `[код markov.py:2417-2422]`;
   5. `_pick_global_start` → `weighted_start3_choice` → `_roll_exploration` + выбор;
   6. `rng.randint` на позицию вклейки отложенного якоря `[код markov.py:2503]`;
   7. на каждом шаге проходки: ролл прыжка (**только** после 5 токенов — `and`-цепочка проверяет счётчики до ролла `[код markov.py:2140-2148]`), ролл order-mix (только при непустом order-3 пуле и ненулевой ручке), затем `weighted_next_choice`: 1 `rng.random()` на исследование, +2 при исследовании (`sampled_exploration`), и либо один `rng.choices`, либо **`rng.expovariate` на каждого кандидата пула**;
   8. швы: `pick_splice_connective` = `rng.random()` + `rng.choice`; вклейка якоря — `pick_jump_connective` без silent-ролла `[код markov.py:2108]`.
3. Verbatim-дописка — вложенная проходка с `attempt_budget=2` на **том же** rng.
4. Слот-мутация: `rng.random()` (только при непустом частотном словаре и незаполненном пуле), затем `rng.shuffle(slots)` и `rng.choices` на каждый пробуемый слот.
5. Seeded-блок: один `weighted_index_choice(exploring=False)` на бутстрап + пошаговые выборы.
6. `select_scored_candidate`: `rng.choices` — только если температура >0 и в окне больше одного кандидата `[код response_generator.py:187-200]`.
7. `apply_reply_flavor`: один `rng.random()`.
8. `append_emoji_flavor`: `rng.random()` + `rng.choices`, и **только если статистика эмодзи непуста** `[код response_generator.py:1140-1149]`.

Вне этого генератора — модульный `random` без сида: ролл ответа
`[код reply_pipeline.py:377]`, L1-затравка `[код reply_pipeline.py:654,667]`,
причуды и редкие события. То есть **выбор горячей n-граммы, меняющий всю
генерацию, лежит вне контракта воспроизводимости**.

Места, где важен порядок списков:

| источник | порядок гарантирован | потребитель |
|---|---|---|
| `get_transitions`/`get_transitions3` | `ORDER BY w3`/`w4` `[код markov_repo.py:98,113]` | `weighted_next_choice` (предусловие в комментарии + тест) |
| `get_starts`/`get_starts3` | `ORDER BY` `[код markov_repo.py:47,60]` | `weighted_start2/3_choice` |
| `get_states` | `ORDER BY` `[код markov_repo.py:213]` | `ContextStateMatcher` (дополнительно сортирует) |
| `get_seed_forward` / `get_reverse_transitions` | `ORDER BY` `[код markov_repo.py:158,135]` | seeded-сборка |

| свёртка кэша | `bisect` по тому же ключу, copy-on-write `[код markov.py:960]` | те же потребители |

# 3. Подозрения, ранжированные по влиянию

## 3.1 Протокол eval измеряет только один из двух режимов работы скорера

**Класс:** eval-vs-prod.
**Что:** `tools/eval/run.py` подаёт `context_tokens=tokenize(prompt)` в каждую
генерацию `[код tools/eval/run.py:236]`, минуя `ReplyPipeline._context_tokens`.
В проде при дефолте `reply_context_only_for_replies=true` контекст получают
только реплаи и прямые обращения `[код reply_pipeline.py:174,629]`.

**Чем доказано:** `[замер 2×300, §1.2]`. Без контекста `context_relevance`
тождественно 0 у всех кандидатов, решающей становится длина (0.450 пулов) и
анти-цитата (0.317); окно отбора расширяется с 2.40 до 3.18 кандидатов,
доля побед лучшего падает 0.697 → 0.627, доля «пул целиком в окне» растёт
0.080 → 0.120.

**На какие вердикты влияло:** на все. Метрики `context_anchored_win_rate`,
`affinity_without_copy`, `context_win_given_top` в бесконтекстном режиме не
определены; калибровки `CONTEXT_RELEVANCE_WEIGHT=1.6`,
`SELECTION_SCORE_MARGIN=0.3`, `context_start_affinity=6.0`,
`context_anchor_splice_probability=0.25`, `context_jump_boost=2.0` подбирались
на режиме, где они все работают. В бесконтекстном режиме пять из этих ручек
инертны, а margin 0.3 отсекает меньше.

**Цена починки:** два независимых шага. (1) Счётчик в телеметрии «ответ собран
с контекстом / без» — ~10 строк, 1 ч; без него доля режима в проде остаётся
неизвестной, и приоритет шага (2) не с чем сверить. (2) Арм матрицы с пустым
контекстом — ~40 строк в `tools/eval/run.py` (или флаг арма), 4–6 ч с
перепрогоном C0. Отдельная фаза не нужна, но базлайны придётся считать по двум
режимам.

**Статус: закрыто M3R-140** (`pre-w15-measurement-hygiene`, 2026-08-14). Оба
шага сделаны: счётчик режима (`ctx_generation_share`, виден в `/stats`) и флаг
прогона `--context-mode {ctx,noctx}` — режим фиксирован на прогон, назван в
шапке отчёта, в JSON и в имени файла. Реализовано **флагом, а не армом
матрицы**: арм считал бы дельты noctx против ctx-базлайна C0, то есть против
другой шкалы (§1.2). Гейт, объявивший `requires_both_modes`, при одномодовом
прогоне отдаёт `insufficient data`. Что **не** сделано и ждёт: сама доля режима
в проде (копится только с рестарта) и noctx-базлайн C0 (прогон принадлежит
первому гейту, которому он понадобится).

**Риск не чинить:** любая последующая настройка скорера продолжит
оптимизировать компоненту, которой в части ответов нет вовсе, — и «часть» эта
до сих пор не измерена.

## 3.2 Две подсистемы выключены данными, а не ручками, и молчат об этом

**Класс:** тихие переключения + наблюдаемость.

**(а) Фаза 5 (lexical anchoring) в проде недостижима.** `rank_seeds` возвращает
`[]` при `n_docs <= 0` `[код markov.py:1652-1654]`. На снимке
`markov_token_df` — **0 строк**, `n_docs = 0` у всех четырёх чатов
`[замер SQL]`. Значит даже при `markov_seeded_candidate_ratio > 0` ветка
пропускается целиком, без лога.

**(б) Канал L1 «локальные мемы» не отдаёт ничего.** `get_hot` при живых
дефолтах (`min_count=3`, `recency_share=0.5`) возвращает пустой список
`[замер SQL: 0 строк; при 2/0.0 — 7, при 1/0.5 — 5]`. Следствия: `start_source
= "seed"` недостижим `[замер: 0.000 в шести армах]`; `protected_tokens` слот-
мутаций пуст, то есть гард «мемы должны оставаться дословными»
`[код slot_mutation.py:154]` не защищает ничего; `markov_hot_ngram_meme_ordering`
переупорядочивает пустой список.

**На какие вердикты влияло:** гейт продвижения M2R-430 планировалось закрывать
на накопленном на проде df — но df не копится (таблица пуста через месяц после
миграции 020). Вердикт фазы 4 по C3 приписывает арму эффект комбинации
`meme_ordering + collocation weights`, тогда как первая половина по построению
не может двигать ни одну автоматическую метрику (§2.1).

**Цена починки:** (а) — проверить, пишется ли `markov_token_df` на живом проде
(диагностика, 1–2 ч; если не пишется — правка learn-пути, отдельный change);
(б) — добавить счётчик «канал вернул пусто» в телеметрию, ~15 строк, 1 ч; и
отдельным решением пересмотреть дефолты порогов горячести.

**Наблюдаемость закрыта M3R-141** (`pre-w15-measurement-hygiene`, 2026-08-14):
`seed_ranking_asked` / `seed_ranking_no_corpus_rate` и `hot_ngram_draws` /
`hot_ngram_empty_rate` — пары «спросили / данных нет», обе видны в `/stats`.
Отсутствие знаменателя (`None`) означает «канал не спрашивали», измеренный ноль
— «спросили и ответил»; до этого оба случая читались одинаково. Сама
неработоспособность **не вылечена** и лечится другими задачами: (а) — окном
накопления df после рестарта, (б) — свипом порогов горячести M3R-145.

**Риск не чинить:** фаза 5 будет промоутиться по замерам на оконно-
аппроксимированном df, которого в проде не существует.

## 3.3 Телеметрия временнóй смеси сообщает «инертна», когда смесь меняет каждый восьмой ответ

**Класс:** гейт/метрика измеряет не то + наблюдаемость.

**Что:** `TemporalBlend.blend` при пустом коротком слое возвращает
`BlendedPool(long_p, 0.0)` `[код temporal.py:178-180]` — то есть **заменяет
сырые счётчики на log-сжатые нормированные вероятности**, а `displacement`
объявляет нулём. `blend_step_coverage` и `mean_blend_displacement` заведены
ровно для того, чтобы отличать «ручка выставлена» от «ручка работает»
`[код markov.py:366-374]` — и именно этот случай они показывают как «не
работает».

**Чем доказано:** `[замер blend_probe, 120 генераций, сид 42]`: при
`markov_alpha_* = 0.5` совпало 105/120 ответов, то есть **12.5% ответов
изменились**, при `applied_alpha=0.50`, `max blend_step_coverage=0.000`,
`max mean_blend_displacement=0.000`. На снимке `s_updated_at` NULL во всех
строках `transitions` `[замер SQL]`.

**На какие вердикты влияло:** фаза 3 измерялась на реконструированной
temporal-фикстуре, и это честно оговорено. Но любой будущий прогон фазы 3 на
основном снимке (или на проде, где короткий слой ещё не набран) увидит
изменённое поведение с телеметрией «coverage 0.0%, shift 0.0000» — что уже
напечатано в отчёте C3 `docs/eval_reports/eval_2026-08-13_phase4-verdict.md:37`
и читается как «смесь выключена».

**Цена починки:** добавить третью метрику — расхождение blended-весов с сырыми
счётчиками (а не с `long_p`), ~10 строк в `temporal.py` + поле трассы, 2–3 ч.

**Риск не чинить:** включение alpha будет выглядеть безопасным по телеметрии
именно в тот момент, когда оно меняет сэмплинг сильнее всего.

## 3.4 Seeded-ветка обходит весь хвостовой конвейер, а не только финализацию

**Класс:** обход общих конвейеров. Прецедент подтверждён и расширен.

**Что:** `_append_seeded_candidates` зовёт `detokenize` сразу после
`generate_seeded_candidate` `[код response_generator.py:605-607]`. Пропущены
все четыре шага хвоста **и** все четыре гейта формы `_finalize_attempt`.

**Чем доказано:** `[замер seeded, n=421]` терминальная пунктуация у 22.8%
против 91.7% у органических; **4.5% seeded-кандидатов начинаются с
пунктуации** (у органических 0.0%) — это отсутствие `strip_leading_punctuation`,
которого предыдущее ревью не отметило. Средний `completion` 0.053 против 0.317,
`verbatim` 0.435 против 0.055, `total` 0.837 против 1.216, win 0.109 против
0.175. Доля победителей с терминальной пунктуацией падает 1.000 → 0.907.

**На какие вердикты влияло:** M2R-430 (см. `REVIEW_2026-08-13.md` §2).

**ЗАКРЫТО 2026-08-14** (change `pre-w1c-seeded-ordering-and-routes`, M3R-101).
Хвостовой конвейер и четыре гейта формы выделены из `_finalize_attempt` в
`finalize_candidate_tokens`; обёртка, собирающая `_GenerationAttempt`, ужалась
с 96 строк до 40. Seeded-ветка идёт через то же тело. `generation_hash` при
нейтральном дефолте `ratio=0` не сдвинулся, как и предсказано.

**Любые числа фазы 5, снятые до этого пакета, с послепакетными несравнимы:**
гейт измерял пропущенную финализацию, а не идею. Перезамер — за M2R-430 после
верификации df.

Побочно найдено при написании тестов: гейт `low_diversity` через этот конвейер
почти недостижим — `trim_repetitive_tail` идёт первым и срезает хвостовой
повтор раньше, чем гейт его увидит `[замер: ["кот"]×12 и «восемь одинаковых
плюс четыре разных» доходят до гейта подрезанными и проходят]`. Гейт ловит
только вырождение в **начале** ответа.

## 3.5 Verbatim-дописка — самый активный канал конвейера и полностью невидим

**Класс:** обход конвейеров + наблюдаемость.

**Что:** `_extend_verbatim_candidate` собирает `base + связка + tail` и
применяет только `finalize_reply_ending` `[код response_generator.py:499-504]`
— без `trim_repetitive_tail`, `trim_to_sentence_boundary`,
`strip_leading_punctuation` и без гейтов формы (перепроверяются только гейты
дублей и точной цитаты).

**Чем доказано:** `[замер]` **1.313 дописки на генерацию** в `ctx` и **1.517**
в `noctx` при 4.5–5.3 принятых кандидатах — шов несёт ~28% кандидатов. Успех
дописки 100% (все вызовы вернули текст). При этом шов дописки **не
инкрементирует `jump_count`** (тот берётся из трассы исходной проходки
`[код response_generator.py:857]`), поэтому измеренная доля победителей со швом
(0.543 / 0.363) — нижняя оценка.

**На какие вердикты влияло:** метрика `connective_reply_rate`, которой
калибровались `context_anchor_splice_probability` и `order_mix_probability`
(порог «связочного тика» ~0.8), считает только швы проходки. Реальная доля
ответов со швом выше на величину дописок.

**Цена починки:** учитывать дописку в `jump_count` либо завести отдельный
счётчик в трассе — ~10 строк, 1–2 ч.

**Риск не чинить:** решения о «связочном тике» принимаются по заниженному
числу.

## 3.6 Гейт `meme_regression_pass` требует удачи, а не качества

**Класс:** гейт измеряет не то. Прецедент из `REVIEW_2026-08-13.md` §4,
подтверждается косвенно.

**Что:** гейт требует, чтобы **каждый** из 27 мемов воспроизвёлся хотя бы раз
`[код tools/eval/metrics.py:226-239]`. 16 из 27 имеют поддержку в одно
сообщение; состав невоспроизводимых плавает между прогонами.

**Новое:** мемы набора выводились из «top hot / verbatim n-грамм» снимка
`[код tools/eval/prompts.py:8-11]`, а `chat_hot_ngrams` на снимке содержит
32 строки с максимальным счётчиком 4 `[замер SQL]` — то есть «hot»-половина
источника мемов сама почти пуста, и набор фактически собран из verbatim-n-грамм
с поддержкой 1.

**Цена починки:** порог поддержки при генерации набора + метрика «доля
воспроизведённых» вместо «все» — ~30 строк в `prompts.py`/`metrics.py`,
перегенерация набора (меняет `version`), 4–6 ч; требует решения, потому что
ломает сопоставимость с прошлыми отчётами.

**Риск не чинить:** гейт остаётся стабильно красным по причине, которую не
измеряет.

**Форма распределения поддержки измерена 2026-08-23** (`derive-phrase-index`,
`tools/eval/phrase_census.py` на прод-копии) и объясняет, почему набор собрался
из поддержки 1 не по недосмотру, а по устройству корпуса: контентных фраз в
цепи **43 229**, из них с поддержкой ≥3 — **831**, ≥5 — **281**. Хвост
единичных фраз составляет подавляющее большинство. Порог поддержки при
перегенерации набора выбирать надо с этим числом на виду, а не наугад.

## 3.6а Фразовый индекс: новый источник данных без читателей

**Класс:** наблюдаемость (превентивно).

`chat_phrase_ngrams` (миграция 022, change `derive-phrase-index`) — пер-чатовый
индекс контентных би/триграмм со всевременным счётчиком. Записан здесь на
будущее, а не как дефект: **у него по построению нет читателей** до фразового
маршрута M3R-210, и в §3.2 живёт ровно тот класс, к которому он иначе
причислится по ошибке — «канал молчит, и непонятно, выключен он данными или
ручкой». Здесь ответ известен заранее: читателя нет вовсе, ручки тоже нет.

Индекс **производен от `transitions`** и пересобирается целиком суточным
пассом, поэтому собственной истории у него нет и разойтись с цепью он не может.
Проверять его состояние следует не по нему самому, а сверкой с
`tools/eval/phrase_census.py` — совпадение чисел и есть его инвариант
(операционные числа: `docs/eval_reports/eval_2026-08-23_phrase-index-operational.md`).

Путь генерации правкой не затронут — ни `markov.py`, ни
`response_generator.py`, ни `reply_pipeline.py`; `generation_hash` не сдвинулся.
Правило §5 о синхронном обновлении карты здесь не срабатывает, и запись сделана
не по нему, а чтобы новая таблица не читалась как забытая.

## 3.7 Два незакреплённых инварианта порядка, от которых зависит розыгрыш

**Класс:** неявные инварианты без теста.

**(а) `get_word_frequencies` не имеет `ORDER BY`** `[код markov_repo.py:234-241]`,
а `pick_replacement` строит `pool`/`weights` в порядке словаря и передаёт их в
`rng.choices` `[код slot_mutation.py:178-200]`. Порядок влияет на результат
розыгрыша при фиксированном сиде. Хуже: `_absorb_message` **дописывает** новые
слова в конец словаря и корзины окончания `[код learning_service.py:586-593]`,
поэтому тёплый кэш и свежее чтение из SQL дают **разный порядок** — то есть
`generation_hash` (холодный старт) и прод (тёплый кэш) сэмплируют мутации из
по-разному упорядоченных списков. `frequencies_by_ending` явно опирается на
«порядок вставки не меняется» `[код slot_mutation.py:213-215]`, но источник
порядка не закреплён ничем.

**(б) `chat_hot_ngrams.get_hot` сортирует `ORDER BY 4 DESC` без вторичного
ключа** `[код chat_hot_ngrams_repo.py:81]`, результат идёт в
`random.choice(hot_ngrams)` `[код reply_pipeline.py:667]`. Тай-брейк не
определён. Сейчас безвреден, потому что список пуст (§3.2б).

**ЗАКРЫТО 2026-08-14** (change `pre-w1c-seeded-ordering-and-routes`, M3R-144) —
**с поправкой к диагнозу этого раздела.**

Предписанная выше починка (`ORDER BY` + вторичный ключ) при реализации
оказалась **no-op**, и лечила не то:

- `GROUP BY w3` в SQLite отдаёт строки в порядке ключа группировки при обоих
  планах, которые получает запрос (`USE TEMP B-TREE FOR GROUP BY` и поиск по
  индексу) — то есть холодное чтение `get_word_frequencies` было упорядочено
  всегда `[замер: выдача с ORDER BY и без совпадает; на прод-копии
  words == sorted(words) во всех чатах, включая 8892-словный]`;
- `get_hot` — то же: план идёт по первичному ключу, чей порядок совпадает с
  порядком n-граммы, поэтому доопределение тай-брейка тождественно.

**Расхождение было только между тёплым кэшем и холодным чтением**, и закрыто
оно на стороне потребителя: `pick_replacement` сортирует пул перед розыгрышем,
после чего исход не зависит от порядка входа вообще. `ORDER BY` и вторичный
ключ внесены как закрепление контракта на слое репозитория — в докстрингах и
тестах помечено, что сегодня они ничего не меняют.

Хеш **не сдвинулся** ни на одном из трёх измерений пакета, перезаморозка не
потребовалась. Это выявило более общий дефект: `generation_hash` гоняет только
холодный старт и потому не видит расхождений тёплого пути по построению —
заводилось как O5, закрыто 2026-08-23 (`docs/CLOSED.md`): гард остался
холодным, а инвариант «тёплый == холодный» держат два теста, граница между
ними — в §7 `CLAUDE.md`. Доказательством правки служит не хеш, а тест
`test_warm_frequency_cache_draws_like_a_cold_read` (без правки пути расходятся
на сиде 0). Подробности — `docs/eval_reports/eval_2026-08-14_w1c-hash-package.md`.

## 3.8 Скорер награждает концовку, которую сам конвейер потом срезает

**Класс:** обход конвейеров / внутренняя несогласованность.

**Что:** `finalize_reply_ending` дописывает точку всем ответам
`[код markov.py:631-632]`, `completion_quality` даёт за неё +0.35
`[код candidate_scorer.py:199-200]`, а `apply_reply_flavor` с вероятностью
`0.25 × strength` эту точку снимает `[код reply_flavor.py:12,79]`.

**Чем доказано:** `[замер]` 100% победителей заканчиваются терминальной
пунктуацией; при `reply_flavor_strength=1.0` **25% отправленных ответов**
теряют её обратно. Размах `completion_quality` в пуле — 0.122–0.151, то есть
компонента почти константна и решает 5.7% (с контекстом) пулов.

**Цена починки:** ничего не чинить, задокументировать: это осознанный
косметический слой. Но при любой правке `completion_quality` (в том числе при
починке seeded, §3.4) надо помнить, что бонус за точку частично декоративен.

**Риск:** низкий; включён в список, потому что §3.4 предлагает лечить seeded
именно этим бонусом.

## 3.10 Анти-повторная память запоминает не то, что отправлено

**Класс:** обход конвейеров, мелкий.

**Что:** `remember_recent_reply(state, chat_id, reply_text)` вызывается с
исходным текстом `[код reply_pipeline.py:463]`, а отправлено могло быть

не попадает.

чат и почти нулевым весом `recent_penalty` (§3.11) — поэтому пункт последний.

## 3.11 `recent_penalty` мёртв не только в eval

**Класс:** eval-vs-prod, с обратным знаком к ожидаемому.

Предыдущее ревью пометило `recent_penalty` как «жива в проде, невидима в
замерах». Замер с тёплой памятью это **не подтверждает**: при 300
последовательных генерациях с ведением `recent_replies`/`recent_short_replies`
по правилам конвейера среднее значение штрафа 0.004, максимальный размах в
пуле 0.016 при окне отбора 0.3, доля пулов, где штраф решает, — 0.000;
изменилось 4/300 (`noctx→live`) и 5/300 (`ctx→livectx`) ответов
`[замер live/livectx]`. Гейт точного повтора сработал 1 раз на 300.

**Оговорка:** симуляция отвечает на случайные промпты, реальный чат тематически
связнее, поэтому это оценка снизу. Но порядок величины — сотые доли при пороге
0.3 — говорит, что компонента не может изменить отбор, а не что она слабая.

**Следствие для прошлых вердиктов:** оговорка «в проде эта компонента живая» в
`REVIEW_2026-08-13.md` §0 требует поправки; систематического искажения прошлых
eval со стороны `recent_penalty` измерением не обнаружено.

# 4. Карта скрытых связей

Пары «ручка A меняет смысл ручки B», не читаемые из реестра.

| A → B | механизм |
|---|---|
| `reply_context_only_for_replies` → **весь контекстный блок** | при `true` непрошеный ответ на не-реплай обнуляет `context_relevance`, `reply_context_bias`, `reply_context_start_bias`, `context_start_affinity`, `context_jump_boost`, `context_anchor_splice_probability` и оба контекстных реджекта разом `[замер §1.2]` |
| `verbatim_extension_share` (0.8) → `verbatim_penalty_strength` (порог 0.6) | штраф реально кусает только полосу доли корпусных 4-грамм [0.6, 0.8): всё что выше — дописывается и перестаёт быть цитатой. Замер: 16–19% кандидатов со штрафом >0, **ни одного** на максимуме 1.5 `[замер]` |
| `SELECTION_SCORE_MARGIN` → `candidate_selection_temperature` | окно отсекает пул до софтмакса; при среднем 2.4–3.2 кандидата в окне температура почти нечего размазывать — отсюда её инертность `[код registry.py:193]` |
| наличие контекста → `SELECTION_SCORE_MARGIN` | без контекста скоры сближаются (компонента с размахом 0.5 исчезает), в окно попадает на 33% больше кандидатов, и один и тот же margin означает более случайный отбор `[замер]` |
| `mood` → `randomness_strength` / `length_mode_weights` / `reply_flavor_strength` / `markov_alpha_*` | mood — единственный вход, который одновременно сдвигает случайность (`randomness_delta`), веса длины, силу вариатора концовки `[код mood.py:75-95]` и **выбор alpha временнóй смеси** `[код response_generator.py:312-319]`. В eval mood всегда отсутствует → всегда «calm» |
| `length_mode` → `natural_length` скорера | режим двигает полосу пика, поэтому одна и та же длина кандидата получает от 0.5 до 1.0 в зависимости от одного `rng.choices` в начале генерации `[код candidate_scorer.py:216-230]` |
| `length_context_adaptation` + `intonation_profile_strength` + mood | три множителя на одном векторе весов длины, применяются последовательно (профиль → mood → зеркалирование) `[код response_generator.py:394-419]`; профиль при этом ещё и укорачивает ответы (замер 2026-07-21) |
| ретенция `messages` (1000) → IDF → `context_relevance` | IDF считается по окну удержанных сообщений `[код learning_service.py:454]`, а цепь помнит вчетверо больше. Токен, которого нет в окне, получает максимальный IDF `[код candidate_scorer.py:294-295]` — то есть ретенция напрямую задаёт шкалу сильнейшей компоненты скорера |
| `STATS_REBUILD_EVERY_MESSAGES` (50) → `context_relevance` | IDF в активном чате отстаёт до 50 сообщений; в тихом — не пересобирается неделями `[код learning_service.py:558]` |
| `markov_cache_incremental` → слот-мутации | тёплый кэш частот дописывает новые слова в конец словаря, холодное чтение отдаёт SQL-порядок; порядок влияет на розыгрыш замены (§3.7а) |
| `hot_ngram_min_count`/`recency_share` → `slot_mutation_probability` | пороги горячести определяют `protected_tokens`; при пустом списке мутации свободно ломают мемы `[код response_generator.py:369-377]` |
| `markov_alpha_*` → `pool_diagnostics` → `markov_entropy_temp_gain` | при включённой смеси энтропия считается по смешанным весам `[код markov.py:2224-2229]`, то есть фаза 2 отвечает на распределение, созданное фазой 3 |
| `markov_interp_order2_weight` → **все sampling-ручки** | β — единственная ручка, создающая среднюю зону энтропии, а `markov_entropy_temp_gain`, `candidate_selection_temperature` и `markov_alpha_*` имеют рычаг только в ней. То есть при β=0 они инертны **по построению корпуса**, а не по своей слабости, и их прошлые вердикты (фазы 2/3) сняты в условиях, где механизма для них не существовало. Ре-замер температуры поверх победившей β — M2R-910, отдельный гейт |
| `markov_interp_order2_weight` → `order_mix_probability` | обе читают проекцию `(w2, w3)` того же состояния и обе расширяют выбор, но по-разному: order-mix **заменяет** пул order-3 на order-2 целиком с вероятностью ручки, интерполяция **смешивает** их на каждом шаге. Включённые вместе они конкурируют за один шаг; совместный замер в грид фазы 9 не входит |
| `markov_short_half_life_days` → долговечность данных | единственная ручка реестра, чьё изменение уничтожает накопленное `[код registry.py:313-318]`, и при глобальном /set — во всех чатах (§3.9б) |
| `order_mix_probability` → `context_jump_boost` | order-mix уводит шаг в более широкий order-2 пул, а буст прыжка существует, чтобы рвать корпусный ретрейс после якоря; обе ручки лечат одну болезнь (ветвление 1.03 у order-3) с разных сторон `[код registry.py:451-466]` |
| `reply_flavor_strength` → `completion_quality` | §3.8 |
| `emoji_append_chance` → анти-повтор | `normalize_reply_for_repeat` специально снимает хвостовые эмодзи, чтобы кандидат совпал со своей отправленной формой `[код response_generator.py:203-210]` — связь учтена в коде, ломается при новых хвостовых слоях |

# 5. Как поддерживать актуальность

Карта попадает под общее правило проекта «доки обновляются вместе с фазой».

**Перегенерируется харнессом** `tools/sweeps/genmap_2026-08-13.py`:

```bash
for a in ctx noctx live livectx seeded hotseed; do
  python tools/sweeps/genmap_2026-08-13.py run --arm $a --generations 300 --seed 42 --out $a-42.json
done
python tools/sweeps/genmap_2026-08-13.py report ctx-42.json noctx-42.json live-42.json livectx-42.json
```

Таблицы, которые он даёт целиком: §1.2 (сравнение режимов), §1.3
(распределение попыток), §1.4 (`start_source` и win-rate), §1.5 (доли дописок,
мутаций, концовок), §2.1 в части замеров, §2.2 в части «связывает / не
связывает».

**Проверяется отдельными запросами к снимку** (SQL, §3.2, §3.6, §2.1
`fuzzy_context_casefold`): пустота `markov_token_df`, `n_docs`, выдача
`get_hot` при разных порогах, число casefold-коллизий состояний, `s_updated_at`.
Это разовые проверки на 10 строк — их место в скретчпаде проверяющего, а не в
репозитории.

**Только руками:**

- §1.1 (трасса) и §1.6 (порядок RNG) — читаются из кода; обновляются при любой
  правке `response_generator.py` / `markov.py` / `reply_pipeline.py`;
- §1.5 (список веток мимо конвейера) — новая ветка добавляется сюда вместе с
  собой;
- §3 (подозрения) — закрытая находка помечается ссылкой на change, а не
  удаляется;
- §4 (связи) — по определению не полна и пополняется по мере находок.

**Что делает карту устаревшей мгновенно:** смена дефолта любой ручки со
статусом «живая», включение любой фазы 2–5, изменение
`reply_context_only_for_replies`, новый снимок прод-копии.
