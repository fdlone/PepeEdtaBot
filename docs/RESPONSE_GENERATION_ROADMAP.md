# Дорожная карта улучшения генерации ответов

> Авторы: совместный анализ Claude (Tech Lead / QA) + Codex (Senior Engineer / Reviewer)
> Дата: 2026-06-20
> Статус: согласованный план (изменения в код не вносились)
> Источники: `docs/RESPONSE_GENERATION_IMPROVEMENT_PLAN.md`,
> `docs/GENERATION_IMPROVEMENT_PROPOSAL.md` + независимый разбор кодовой базы и
> QA-валидация по реальному коду.

## 1. Где мы сейчас (консолидировано)

Пайплайн генерации размазан по трём слоям, оркестрация находится в
Telegram-хендлере:

- `app/handlers/learning.py` — решение об ответе, сбор контекста, до **10**
  внешних попыток, приём **первого** валидного кандидата;
- `markov.py:generate_text` — до **8** внутренних ретраев → в худшем случае
  **~80 полных генераций на одно сообщение**;
- `app/services/learning_service.py` — запись сообщений и exact-copy против
  последних 500 нормализованных сообщений.

Нет `ResponseGenerator`, скоринга кандидатов, пула кандидатов, injected RNG,
offline-харнесса. Существующие документы это в целом описывают верно, но
**недооценивают алгоритмические дефекты**, подтверждённые по коду (раздел 2).

## 2. Подтверждённые дефекты (QA-валидация по коду)

| # | Где | Проблема | Эффект |
|---|---|---|---|
| D1 | `markov.py:798` | `if strength >= 1.5 and not context_tokens and len(generated) > 10 and jump_count == 0: return ""` | при дефолтной `randomness=2.0` связный длинный ответ без «прыжка» отбраковывается — движок принудительно поощряет менее связную ветку |
| D2 | `markov.py:677-698` | при «прыжке» новое состояние присваивается и идёт `continue`, но стартовые токены прыжка **не добавляются** в `generated` | разрыв связности вывода |
| D3 | `markov.py:272-273` (`weighted_next_choice`) | `if random.random() < explore_probability: return random.choice(population)` | равномерный выбор в обход всех весов (частоты/контекст/штрафы); при дефолте ~48% переходов, до ~66% на эскалации |
| D4 | `learning.py:146` vs `:244` | входящее сообщение обучается в модель (`record_message`) ДО генерации ответа на него | контаминация модели промптом, рост echo/copy |
| D5 | `markov.py:779-783` | `set.pop()` для вытеснения удаляет произвольный элемент | недетерминизм, мешает воспроизводимости |

## 3. Принцип очерёдности

> Сначала чиним то, что прямо портит связность и воспроизводимость (дёшево,
> низкий риск), затем делаем качество **измеримым**, и только потом — дорогие
> архитектурные изменения и многокандидатный скоринг.

Это сознательное расхождение с обоими документами: они ставят выделение
`ResponseGenerator` и многокандидатную генерацию в начало (GEN-001/004,
Этап 1 в `IMPROVEMENT_PLAN`). Мы переносим их ниже, потому что реальные дефекты
качества лежат в самом алгоритме (раздел 2).

## 4. Этапы

### Фаза 0 — Дефекты связности и контаминации (🔴 P0, дёшево, низкий риск)

- **0.1 + 0.2 (атомарно).** Убрать forced-jump-отбраковку (D1) **и** отключить
  текущую ветку «прыжков» (D2) одним изменением. Эти два шага неразделимы: при
  выключенных прыжках, но сохранённой D1, любой длинный ответ без контекста при
  дефолтной `randomness` отбраковывался бы. Splice с дописыванием стартовых
  токенов в Фазе 0 **не делаем** — это явная конкатенация фраз с проблемами
  лимитов токенов/символов; откладываем до отдельного дизайна. *(S / Low)*
- **0.3.** Генерировать ответ по модели **до** обучения на входящем сообщении
  (D4), разнеся `record_message` (`learning.py:146`) и `generate_text` (`:244`).
  При этом обязательно:
  - гейт «достаточно данных» использует **до-сообщенный** объём модели; сообщение,
    пересекающее порог, обучается, но **не** триггерит ответ на самого себя
    (ответ — со следующего сообщения);
  - каждое learnable-сообщение персистится **ровно один раз** на всех путях,
    включая early-return и провал генерации (не «теряем» обучение, если ответа
    нет);
  - кандидат, равный нормализованному текущему входящему сообщению, явно
    отклоняется (т.к. `is_verbatim_copy()` смотрит только в персистентный кэш, а
    текущее сообщение там ещё отсутствует). *(M / Medium)*
- **0.4.** Валидировать **фактический** возвращаемый текст после усечения по
  `max_chars`, а не до-detokenize буфер токенов: сейчас `generated` может
  содержать финальный токен, который `detokenize(max_chars)` опускает, и проверки
  diversity/context работают по токенам, отличным от реально отправляемого
  текста. *(S / Low)*
- **Гейт (regression-тесты до изменений):**
  - сообщение, пересекающее порог, обучается, но не используется для ответа на
    себя;
  - точная копия текущего входящего сообщения отклоняется;
  - learnable-сообщения персистятся, даже когда ответ не генерируется;
  - удаление D1 и отключение прыжков «приземляются» атомарно.

### Фаза 1 — Детерминизм и измеримость (🔴 P0, фундамент)

- **1.1.** Injected `random.Random` вместо глобального `random`; заменить
  `set.pop()`-вытеснение (D5) на детерминированную стратегию; стабильный порядок
  SQL/population. *(M / Low)*
- **1.2.** Инструментация: компактный trace (число попыток, использованный
  порядок, jump_count, причина отказа) — без утечки текста. Реализовать
  **обратносовместимо**: новый/внутренний API возвращает result-dataclass, а
  публичный `generate_text` сохраняет текстовый контракт через тонкую обёртку
  (иначе придётся мигрировать всех вызывающих и тесты). *(S-M / Low)*
- **1.3.** Offline-харнесс (`tools/eval_generation.py`) на синтетическом корпусе
  и фиксированном seed: `empty_rate`, distinct-1/2, доля повторяющихся
  би-/триграмм, latency, context-copy, среднее число попыток. Зафиксировать
  **post-Phase-0 baseline** для всех последующих изменений алгоритма. (Фаза 0 —
  это исправление корректности, которое не должно ждать полного харнесса; при
  желании можно снять и pre-fix baseline до Фазы 0.) *(M / Low)*
- **Расхождение с доками:** offline-оценка должна идти **до** скоринга
  кандидатов, а не после.

### ✅ Между Фазой 1 и Фазой 2 — STRUCT-001: техдолг структуры (ВЫПОЛНЕНО)

> **Статус: выполнено** (flat-раскладка). Корневые модули перенесены в пакеты
> `app/config`, `app/core`, `app/infrastructure`, `app/domain`, `app/presentation`;
> seed-скрипты → `tools/`. Поведение и baseline сохранены, 278 тестов зелёные.
>
> Исходно: отдельный шаг ПОСЛЕ Фазы 1 и ДО Фазы 2, не смешивая с генерацией.

**Проблема:** незавершённая миграция в пакет. Создан структурированный пакет
`app/` (handlers/services/repositories/...), но ~13 модулей ядра лежат плоско в
корне проекта: `markov.py`, `db.py`, `text_utils.py`, `bot_policy.py`,
`bot_messages.py`, `config_registry.py`, `pivo.py`, `pivo_templates.py`,
`runtime_config.py`, `runtime_state.py`, `seed_db.py`, `seed_diverse.py`,
`settings.py`. Отсюда два «корня импорта» (`from markov import …` рядом с
`from app.services import …`) и рыхлая структура корня.

**Почему между фазами:** Фаза 1 уже стабилизирует генератор (RNG, trace,
харнесс), а Фаза 2+ начнёт активно править алгоритм и (Фаза 3) извлекать
`ResponseGenerator`. Перенос модулей в пакет дешевле и безопаснее сделать на
стабильном генераторе, но **до** крупных правок алгоритма — иначе придётся
двигать активно меняющийся код.

**Содержание шага (отдельный `refactor(structure)` PR, не смешивать с генерацией):**
- Codex-first анализ графа импортов всех корневых модулей.
- План переноса в `app/` (или другой целевой пакет) с сохранением поведения.
- Обновить импорты по всему проекту, `tests/`, `Dockerfile`, CI.
- Опционально: убрать аудит-доки из корня в `docs/` (согласовать с `CLAUDE.md`,
  который ссылается на них по имени).
- DoD: тесты/ruff/mypy/bandit зелёные; поведение не меняется; CI зелёный.

**Риск:** Medium (широкий, но механический diff по импортам). **Эффект:** чистый
корень, единый корень импорта, проще навигация и дальнейший рефакторинг.

### Фаза 2 — Удешевление и выпрямление ретраев (🟠 P1)

- **2.1.** По данным 1.2/1.3 схлопнуть вложенные циклы (10×8) в один сквозной
  бюджет попыток/времени; снизить потолок генераций без потери метрик.
  *(M / Medium)*
- **2.2.** Заменить uniform-«explore» (D3) на взвешенное сэмплирование с
  сохранением штрафов за повторы и контекста. *(M / Medium)*

### Фаза 3 — Архитектура и многокандидатный выбор (🟡 P2)

- **3.1.** Behavior-preserving выделение `ResponseGenerator` (перенос цикла из
  хендлера). *(M / Medium)*
- **3.2.** Начать с **3–5** кандидатов и увеличивать число только если оценка
  (харнесс 1.3) показывает выигрыш в пределах latency-бюджета + консервативный
  скоринг: жёсткие safety-фильтры → completion → repetition → умеренная длина →
  **capped** context-relevance. *(M-L / Medium)*
- **Расхождение с доками:** старт с 6–8 кандидатов преждевременен; capped
  model-confidence обязателен, иначе движок начнёт воспроизводить заученные
  частые фразы.

### Фаза 4 — Естественность, корпус, privacy (🔵 P2-P3)

- **4.1.** Семантика контекста: сделать `context_start_bias` реально влияющим;
  отделить скрытое контекстное состояние от токенов, попадающих в ответ.
  *(L / Med-High)*
- **4.2a.** Окончания фраз (улучшение границ предложений). *(M / Medium)*
- **4.2b.** Фильтрация корпуса/privacy: секреты/email/телефоны/boilerplate
  прямого обращения. Отдельный risk-профиль от 4.2a. *(M / Medium)*
- **4.3.** Капитализация и токенизация (эмодзи, апострофы) **вместе со**
  стратегией совместимости модели при смене токенизации — **только** после
  offline-проверки: может конфликтовать с `NORMALIZE_LOWER` и стилем чата.
  *(оценивать, не предполагать; L / Med-High из-за совместимости модели)*

## 5. Сводная приоритизация

| Приоритет | Задачи | Зачем |
|---|---|---|
| 🔴 P0 | 0.1+0.2, 0.3, 0.4, 1.1, 1.2, 1.3 | убрать баги связности + воспроизводимость + baseline |
| 🟠 P1 | 2.1, 2.2 | дешевле и качественнее генерация |
| 🟡 P2 | 3.1, 3.2 | выбор лучшего кандидата, а не первого |
| 🔵 P2-P3 | 4.1, 4.2, 4.3 | контекст, естественность, privacy |

**Рекомендуемый первый инкремент:** Фаза 0 + 1.1–1.3. После этого все дальнейшие
правки принимаются по числам, а не «на глаз», и убираются самые заметные
источники бессвязности.

## 6. Definition of Done для изменений генерации

1. прогнан offline-харнесс (1.3), метрики приложены (было/стало);
2. `ruff`, `mypy`, `unittest` — зелёные; область `ruff`/`mypy` **явно включает
   `markov.py`** (сейчас он исключён из строгих проверок) — иначе изменения в
   самом сложном файле остаются без статической страховки;
3. новые ветви логики покрыты тестами;
4. при изменении формата модели описана стратегия совместимости (раздел 4.2).

## 7. Что не делать сразу

- Подключать внешнюю LLM без отдельного privacy-решения.
- Переписывать `markov.py` одним большим изменением.
- Начинать с 6–8 кандидатов и/или полного `GenerationProfile` до инструментации.
- Считать distinct-метрики объективным мерилом качества (могут поощрять
  бессвязный «word salad» — нужна слепая попарная человеческая оценка).
- Включать автокапитализацию «по умолчанию» без offline-проверки.
