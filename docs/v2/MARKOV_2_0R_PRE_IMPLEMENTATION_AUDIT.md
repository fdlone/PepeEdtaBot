## 2. Текущая архитектура Markov (1.x)

### Состояние, порядки, вероятности

- Состояния — кортежи строк-токенов; переходы — `(next_token, count)`. Порядки: **order-3**
  (`transitions3`: chat_id,w1..w4,cnt) и **order-2** (`transitions`), старты `starts`/`starts3`.
  Order-1 удалён (миграция 013). Контракт чтения — `MarkovReadPort`, ровно 7 методов
  (`app/core/markov_port.py:25-68`); генератор зависит только от порта.
- **Вероятности нигде не нормализуются** — весами служат сырые `cnt`, температура — через
  степень `weight = max(cnt,1) ** frequency_power` (`app/core/markov.py:574-633`), где
  `frequency_power` выводится из `randomness_strength` и exploration-ролла (`markov.py:487-519`).
- Backoff: order-3 → order-2 двумя путями — «естественный» (пустой пул) и **order-mix valve**
  (с вероятностью `order_mix_probability=0.75` подмена пула на order-2, если тот шире,
  `markov.py:1536-1543`). Дно — order 2.
- Сэмплинг: не-exploring — `rng.choices(weights)`; exploring — экспоненциальная гонка
  `min(key=expovariate(w))`, распределительно эквивалентна пропорциональной выборке,
  но потребляет n затравок вместо 1 (`markov.py:534-553`). Фактическое «уплощение» даёт
  только `frequency_power`.

### Поток генерации

`on_text_message` → `ReplyPipeline` → `ResponseGenerator.generate_with_result`
(`app/core/response_generator.py:477-812`) → до **10 попыток** генерации, цель — **5 кандидатов**
(`GENERATION_ATTEMPT_BUDGET=10`, `CANDIDATE_TARGET=5`), эскалация randomness по попыткам,
попытки ≥5 без контекста. Выбор: софтмакс по `total` с `T=0.7` и порогом отсечения
`SELECTION_SCORE_MARGIN=0.3` (`response_generator.py:120-145`).

Скоринг (`app/core/candidate_scorer.py:127-136`):
`total = completion_quality + natural_length + context_relevance − repetition − recent − verbatim`.
Контекст-компонент — **уже IDF-взвешенный** (`idf_context_relevance:244-284`): стемized-пересечение
с анти-попугай правилом (кандидат ⊆ контекст ⇒ 0), IDF по последним 1000 сообщений
(`build_token_idf`, `log((N+1)/(df+1))+1`).

Стартовые пути (приоритет): seed (hot-ngram канал) → контекстный
(`REPLY_CONTEXT_START_BIAS=2.2` ⇒ p≈0.545; exact 3-грам → exact 2-грам → casefold через
`ContextStateMatcher`) → глобальный (стем-аффинити `CONTEXT_START_AFFINity=6.0` c
анти-парротом). Отложенный якорь: splice с p=0.25. Джампы: max 1, `p=0.12×context_boost 2.0`.
Поверх: mood (EWMA, 4 класса, множители), intonation (дефолт 0 — выключено), reply flavor,
слот-мутации (p=0.15, pymorphy3-гард), verbatim-гейт с каналом расширения, редкие события L3.

Анти-повтор — три слоя: внутри прогулки (visited/seen + штрафы весов), пост-фильтры попытки
(`_finalize_attempt` + 4 причины отказа), меж-ответный (эхо входа, повтор последних 20 ответов).

### Телеметрия и детерминизм (критично для Phase 0/1)

- Есть `GenerationTrace` (`markov.py:152-164`: attempts, order_used, jump_count, rejection,
  start_source, context matches) и `gen_trace_log` (полная построчная трасса запрос/попытка/выбор,
  дефолт выключен, тексты кандидатов внутри — потому и выключен). **Энтропия/branching/confidence
  нигде не считаются** — это чистый gap M2R-010.
- **RNG всюду инжектится** (`random.Random` параметром); прод-путь не воспроизводим
  (свежий `Random()` на вызов, `reply_pipeline.py:415`), но при фиксированном сиде пайплайн
  **воспроизводим бит-в-бит, и это поддерживаемый инвариант**: докстринг
  `reply_pipeline.py:17-18` («порядок обращений к random сохранён дословно»),
  `tools/generation_hash.py` (SHA-256 вывода по фиксированным сидам — гард рефакторингов),
  паттерн «выключенная ручка не потребляет затравку» (`markov.py:1726-1731`, `emoji.py:145-155`).
  Требование `MARKOV_V2_ENABLED=false ⇒ поведение 1.x бит-в-бит` — **выполнимо**, если каждая
  V2-ветка соблюдает этот паттерн.
- Прочие якоря детерминизма: SQL `ORDER BY` на всех чтениях цепи (замена сортировки в процессе),
  insertion-order словарей частот.

### Кэширование (база для M2R-030)

`MarkovGenerator`: 4 LRU-кэша (`_cache3/_cache2/_cache_starts3/_cache_starts2`, лимит 1024)
плюс индекс `ContextStateMatcher`. **Инвалидация — целиком по чату на каждом выученном
сообщении** (`learning_service.py:188` → `markov.py:729-738`), а respond идёт до learn, поэтому
в активном чате почти каждый ответ стартует с холодных кэшей: полные чтения `starts`/`starts3`
(~4.1k/4.5k строк на прод-копии) + по запросу на шаг × до 10 попыток. Кэши `LearningService`
(verbatim-индекс, IDF, частоты) наоборот докатываются инкрементально и не сбрасываются.
Вывод: M2R-030 — не «добавить кэш», а **починить стратегию инвалидации** существующего
(точечная по затронутым state вместо полной), плюс TTL для времязависимого `s_eff`.

## 3. Нормализация и токенизация (фиксированная точка ADR-016)

Пайплайн: `strip_leading_bot_vocative` → `sanitize_text` (`app/core/text.py:102-115`: ссылки →
редакция PII/секретов → @упоминания → маркеры списков → сжатие повторов → пробелы) →
`tokenize` c `TOKEN_RE = r"\w+|[.,!?;:]"` и `lower()` при `NORMALIZE_LOWER=true` (дефолт;
модель приведена к lowercase бэкфиллом 015).

Следствия, на которые опирается 2.0R:

- **Эмодзи и все прочие символы выбрасываются** токенизатором полностью; пунктуация
  `.,!?;:` — самостоятельные токены цепи.
- BOS/EOS нет: стартом становятся первые 2/3 токена сообщения, конец прогулки — только
  исчерпание пула/лимиты. Коллокации и PMI работают по смежным парам внутри выученных
  сообщений (как уже делает `hot_ngrams.py`).
- **Стемминг не участвует в цепи** — только в скоринге/аффинити/IDF (`morphology.py`,
  ~50 русских окончаний, `lru_cache(100k)`). Канонические токены цепи — поверхностные lowercase.
- Verbatim-индекс использует **другую конвенцию границ** (content-токены, casefold, 4-граммы
  без пунктуации) — при реализации PMI/коллокаций не смешивать две конвенции.
- `messages.normalized_text` хранится **с сохранением регистра** (lowercase — только в цепи);
  IDF-документ ТЗ §9.3 («нормализованное сообщение») на практике = токенизация этого текста.

Любая правка `TOKEN_RE`/`sanitize_text` — это смена канонической токенизации, запрещённая
ADR-016 (rebuild невозможен). Мем-регресс-кейс дока 05 обязан прогоняться на этой токенизации.

## 4. Персистентность

### Схема (после 17 миграций)

- Цепь: `starts(chat_id,w1,w2,cnt)`, `starts3(+w3)`, `transitions(chat_id,w1,w2,w3,cnt)`,
  `transitions3(+w4)` — **только целочисленный `cnt`, никаких временных меток** (подтверждено
  DDL и прод-снапшотом). PK-автоиндексы, вторичных индексов нет (сняты миграцией 008).
- Вспомогательные: `messages` (retention 1000/чат, `normalized_text`), `chat_model_volume`
  (инкрементальный объём), `chat_verbatim_ngrams` (WITHOUT ROWID, существование 4-грамм,
  не подрезается), `chat_hot_ngrams`/`chat_emoji_stats`/`chat_user_interactions`
  (`cnt`+`updated_at`, полураспад 7/7/30 дней), `/pivo`-таблицы (chat_hash/user_hash),
  `schema_migrations`.
- Соединение: **одно** `aiosqlite`-соединение + один `asyncio.Lock` на весь процесс; WAL,
  busy_timeout 5000, wal_autocheckpoint 1000. Все запросы сериализованы.
- Прод-копия (`db_prod_copy/markov.db`, 2026-07-13, миграции 001-012): transitions 30 907,
  transitions3 27 317, starts 4 128, starts3 4 482, messages 1 062, 12.9 MB.

### Горячие пути

- **Learn** (одна транзакция на сообщение): insert message + retention delete + upsert
  starts/starts3 + executemany upsert transitions/transitions3 + verbatim-4-граммы +
  chat_model_volume (`database.py:201-349`); затем hot n-grams отдельной транзакцией
  и ленивое обслуживание раз в сутки.
- **Reply**: verbatim-индекс и IDF из кэшей LearningService; `starts3`+`starts` полным чтением
  на попытку (при холодном кэше), `get_transitions3/2` на шаг прогулки.

### Миграционный фреймворк

Автозапуск при старте (`Database.init` → `migrator.run`), файлы `NNN_name.(sql|py)` по имени,
версия — стем в `schema_migrations`, только вперёд, откатов нет; `.sql` атомарен
(BEGIN/COMMIT обёрткой), `.py` — `await apply(conn)` в общей транзакции. Прецеденты стоимости:
**015** (полный rebuild всей цепи через Python-UDF lowercase), **016** (бэкфилл verbatim-таблицы
полным чтением transitions3 в память), 017 (хирургия цепи GLOB-предикатами). Бэкфиллы масштаба
Phase 3/5 — проверенный жанр.

### Retention/GC — фактическое положение

Цепь и `chat_verbatim_ngrams` **никогда не затухают и не удаляются** штатными джобами —
только `/clear confirm` (полный пер-чат wipe 13 таблиц + кэши) и разовые миграции. Полураспад
есть только у flavor-таблиц. Планировщика нет: обслуживание при старте + лениво из learn-пути.
Это ровно посылка ADR-011 (long не затухает) — код ей уже соответствует.

## 5. Privacy, retention, реакции

### Гарантии текущего дизайна (проверены по коду)

1. **Сырой user id не хранится нигде**: `messages.author_id` — константа 0 (миграция 003 +
   хардкод на вставке), пер-пользовательские счётчики — HMAC-SHA256, `/pivo`-профили — Fernet
   (MultiFernet: HKDF-ключ + legacy read-only). Секреты ≥32 символов, валидируются на старте.
2. **Сырой текст не хранится**: колонка `text` удалена (005), остаётся `normalized_text`
   после санитизации (ссылки, PII/секреты, упоминания) и только последние 1000/чат. Но
   n-gram таблицы бессрочно хранят словесный состав всей истории — отсюда «rebuild невозможен»
   (ADR-005 подтверждён кодом).
3. **`chat_id` в БД сырой, в логах — только маска** (HKDF-HMAC, 8 hex; fail-fast если
   маскирование не инициализировано); артефакты репозитория гардит `tests/test_no_real_chat_ids.py`.
4. **`/clear confirm` полон** для текущей схемы (13 таблиц + кэши процесса). Каждая новая
   таблица 2.0R (реверс, df, коллокации, пресеты) **обязана** добавляться в `clear_chat` —
   интеграционный тест ТЗ §19 это закрепит.
5. Пер-пользовательские счётчики затухают (30 дней) и исчезают в нуле; `gen_trace_log`
   с текстами кандидатов выключен по умолчанию.

Для 2.0R: новые структуры не добавляют идентичности (реверс/df/коллокации — те же агрегаты
по чату; пресеты — per-chat). `GenerationDiagnostics` без сырого текста соответствует
практике `GenerationTrace`. Ограничение P6 соблюдаемо без новых механизмов.

### Telegram-реакции (гейт Phase 8) — **НЕ заблокировано**

- Сейчас бот получает **только** `message`-апдейты: `start_polling` без `allowed_updates`,
  единственный не-message обработчик — `errors` (авторезолв aiogram даёт `["message"]`).
- aiogram 3.29 (Bot API 10.1) поддерживает всё нужное: `MessageReactionUpdated`, обсервер
  `message_reaction`, `Bot.set_message_reaction`.
- Минимальные изменения для приёма: зарегистрировать `message_reaction`-хендлер (авторезолв
  сам добавит тип в allowed_updates) + при необходимости навесить middleware на этот обсервер
  (сейчас они только на `dp.message`). **Операционные предусловия:** бот должен быть
  администратором чата (иначе Telegram не шлёт `message_reaction`); реакции самих ботов
  не репортятся (для reward-агрегата неважно — сигнал от людей).

| Требование 2.0R | Состояние в коде | Вердикт |
|---|---|---|

| Best-of-N + финальный scorer (ADR-008) | Есть полностью (10 попыток/5 кандидатов/софтмакс) | **готово, переиспользуется как есть** |

| Repetition/anti-echo | Есть, три слоя | готово |

| Временные слои (§7–8) | **Нет**: у переходов только `cnt`; long-слой фактически уже существует (нес затухающий `cnt`) | миграция M2R-200 добавляет 4 колонки; short строится с нуля |

| Реверс order-2 + seeded (§9) | Нет; но **вход для seeded-кандидатов есть**: seed-путь `_pick_seed_start` (hot-ngram канал) уже встроен в приоритет стартов | таблица+бэкфилл новые; интеграция дешевле, чем предполагает ТЗ |
| IDF-скоринг контекста (§9.7) | **Уже есть** (`idf_context_relevance` + `build_token_idf` по окну 1000 сообщений) | gap только в источнике IDF: окно ↔ инкрементальный df-агрегат §9.3 |
| Телеметрия (§20, M2R-011) | Каркас есть (`GenerationTrace`, `gen_trace_log`, `/stats`) | расширение, не стройка |
| Bounded-кэш (§14, M2R-030) | LRU есть; инвалидация «в ноль» на каждом learn | починка стратегии + время-зависимый `s_eff` |
| GC (§15) | Ничего не удаляется — совпадает с «оба режима off» | строится с нуля, дефолт уже соблюдён |
| Реакции-бандит (§16) | Реакций нет; aiogram готов | строится с нуля, не заблокировано |
| Eval (док 05) | Богатые заделы: `eval_prod` (метрики, инструментация, winner-атрибуция), `generation_hash` (бит-в-бит), методика ≥400 генераций | новый раннер `tools/eval` поверх заделов |
| Флаги/конфиг (§18) | Реестр из 66 ручек с паттерном добавления (5 шагов), chat-overrides, `/set`; дрейф `.env.example` гардится тестами | добавление ключей — механика готова |
| Mood → α-профиль (§8.3) | mood EWMA с 4 классами уже есть | маппинг тривиален |

Итого: **два столпа 2.0R уже стоят** (best-of-N+scorer и контекст/IDF-скоринг), «long-слой» —
это существующие `cnt`. Принципиально новые массы: энтропия, short-слой+blend, PMI/коллокации,
реверс+seed_score, GC, бандит, eval-раннер.

## 7. Точки «нельзя ломать» и переиспользуемые компоненты

**Нельзя ломать:**

1. **Порядок потребления RNG при фиксированном сиде** — контракт (`generation_hash`,
   characterization-тесты). Каждая V2-ветка обязана не потреблять затравки при выключенном флаге.
2. **Каноническая токенизация** (`TOKEN_RE`, `sanitize_text`, lowercase) — ADR-016.
3. **`MarkovReadPort`** — ядро не знает про БД; новые чтения (реверс, s_value) — расширение порта.
4. **Полнота `/clear confirm`** — каждая новая таблица немедленно в `clear_chat`.
5. **Гард-тесты**: `test_no_real_chat_ids`, дрейф `.env.example`↔реестр, характеризационные
   тесты генерации, coverage ratchet 87, mypy strict по `app/`.
6. **Privacy-инварианты §5** (author_id=0, HMAC/Fernet, маскирование логов).
7. Однопоточность БД: одна связка соединение+lock; тяжёлые чтения = блокировка всего.

**Переиспользуется:**

- Весь best-of-N/scorer/отбор; seed-путь стартов; hot n-grams (интеграция мемов);
  mood (α-профиль); `GenerationTrace`/`gen_trace_log` (телеметрия); LRU-кэши (база M2R-030);
  реестр ручек + overrides; migrator с прецедентами бэкфиллов; из eval —
  `copy_database`, инструментация трасс, winner-атрибуция, методика сидов/объёмов,
  `distinct_basis_tokens`-урок, `seed_db`/`seed_diverse` для snapshot_synthetic.

| Риск | Оценка | Смягчение |

## 10. Противоречия и открытые вопросы

1. **`snapshot_temporal` (док 05 §1.1) невозможен до Phase 3 + окна накопления.** Разрез
   по `first_seen`/`s_updated_at` требует колонок, которых нет, и истории, которую нельзя
   восстановить (§8). Затронуты: `freshness_reflection`, построение topical/meme-bait промптов
   «из snapshot_temporal». **Предлагаемое разрешение (в proposal Phase 0):** до появления
   реального temporal-разреза topical/meme-bait промпты строятся детерминированным скриптом из
   `snapshot_full` (частоты + `chat_hot_ngrams` + `chat_verbatim_ngrams` как прокси «известных
   мемов»); `freshness_reflection` помечается в отчётах `insufficient data`; мем-регресс-лист
   фиксируется из текущего среза (возрастной критерий «≥1 года» заменяется на «присутствует
   в полном срезе и в hot-окне не доминирует» до накопления меток). Протокол (док 05) при
   approval дополняется этим пунктом отдельным коммитом.
2. **Свежесть baseline-снапшота.** `db_prod_copy/markov.db` датирован 2026-07-13 (миграции
   001-012), код ушёл вперёд (013-017 применятся при копировании автоматически — механизм
   `copy_database` это уже делает). Вопрос владельцу: замораживать baseline на этой копии или
   снять свежий слепок прод-БД перед M2R-000. Рекомендация: свежий слепок (дешёво, честнее).
   **Решение владельца (2026-08-11): свежий слепок недоступен; baseline замораживается на
   `db_prod_copy/markov.db` (2026-07-13) с миграциями, применёнными при копировании.**
3. **Расположение доков**: мастер-промпт говорит «директория `docs/`», фактически —
   `docs/v2/`. Принято: `docs/v2/` — нормативный путь; аудит и отчёты Phase 0 живут рядом
   (`docs/eval_reports/` — как в доке 05).
4. **Метрики дока 01 §7 vs док 05 §3**: списки не идентичны (01 упоминает `reply_rate`,
   `order_distribution`, `mean_entropy` и др., которых нет в нормативных определениях §3).
   Принято по иерархии: док 05 нормативен для определений; телеметрические величины из 01
   пишутся в отчёт как информационные без статуса метрик-гейтов. Противоречием не считаю,
   фиксирую трактовку.
5. **`aiogram` yanked** — см. §1; отдельный change вне 2.0R.
6. Противоречий «код ↔ ТЗ», требующих остановки, не найдено: ТЗ (§1) корректно описывает
   архитектурное направление, найденные отличия — ожидаемые «цель vs текущее».
