# in-memory-state-eviction Specification

## Purpose
Задаёт требования к состояниям, которые бот держит в памяти между обновлениями: такие состояния должны быть ограничены сверху и уметь забывать неактуальное, не меняя при этом того, что видит пользователь.
## Requirements
### Requirement: Состояние в памяти ограничено по времени и по объёму

Каждое состояние, которое бот накапливает в памяти по ключу, полученному из внешнего события (чат, пользователь, команда), SHALL иметь и предел хранения по времени, и предел по числу записей.

При превышении предела по числу записей система SHALL вытеснять записи, обращение к которым было раньше всего.

#### Scenario: Запись устарела

- **WHEN** к записи не обращались дольше срока хранения
- **THEN** запись удаляется из состояния

#### Scenario: Переполнение

- **WHEN** число записей превышает установленный предел
- **THEN** удаляются записи с самым давним обращением, пока предел не соблюдён
- **AND** записи, к которым обращались недавно, сохраняются

### Requirement: Вытеснение не меняет наблюдаемого поведения

Вытеснение записи SHALL приводить только к повторному получению данных из источника, а не к иному решению системы.

Для кэша прав это означает: после вытеснения права запрашиваются заново, и результат проверки прав для того же пользователя в том же чате остаётся прежним.

#### Scenario: Права проверяются после вытеснения

- **WHEN** запись о правах в чате вытеснена, и в этом чате вызывается команда, требующая прав
- **THEN** права запрашиваются заново
- **AND** решение о доступе совпадает с тем, что было бы при наличии записи

### Requirement: Отказ источника не превращается в выдачу прав

Если данные о правах получить не удалось, система SHALL отказать в доступе.

Ни отсутствие записи в состоянии, ни её вытеснение SHALL NOT приводить к выдаче прав по умолчанию.

#### Scenario: Источник прав недоступен

- **WHEN** запрос прав завершается ошибкой
- **THEN** в доступе отказано

### Requirement: Производные кэши по чату ограничены наравне с прочим состоянием

Кэши, которые система строит по данным конкретного чата — выборки сообщений, индексы, словари, статистические профили, — SHALL подчиняться той же политике, что и остальное состояние в памяти: предел по сроку хранения и предел по числу чатов.

Основание то же самое: число чатов задаётся снаружи, а объём такого кэша растёт вместе с историей чата и ничем не ограничен сам по себе.

#### Scenario: Чат замолчал

- **WHEN** к производным кэшам чата не обращались дольше срока хранения
- **THEN** они удаляются из памяти

#### Scenario: Слишком много чатов

- **WHEN** число чатов с производными кэшами превышает предел
- **THEN** вытесняются кэши чатов с самым давним обращением

#### Scenario: Обращение после вытеснения

- **WHEN** в вытесненном чате снова требуется производный кэш
- **THEN** он строится заново из базы
- **AND** результат совпадает с тем, что был бы без вытеснения

### Requirement: Обновление кэша не превращается в полную пересборку на каждое сообщение

Если известен вклад нового сообщения в производный кэш, система SHALL обновлять кэш этим вкладом.

Полный сброс кэша на каждое выученное сообщение SHALL NOT применяться там, где инкрементальное обновление даёт тот же результат: кэш, который гарантированно холодный к моменту использования, не выполняет своей задачи.

Результат последовательности инкрементальных обновлений SHALL совпадать с результатом построения кэша с нуля.

#### Scenario: Сообщение выучено

- **WHEN** система выучила новое сообщение чата
- **THEN** производные кэши чата отражают его содержимое
- **AND** полная пересборка кэша не выполняется

#### Scenario: Эквивалентность инкрементального обновления

- **WHEN** кэш обновлён последовательностью сообщений инкрементально
- **THEN** его содержимое совпадает с построенным по тем же сообщениям с нуля
