## Why

Код-ревью 2026-07-21 (Low, в бэклоге `docs/OPEN.md`): часть числовых ручек объявлена как `_int_min(0)` — нижняя граница есть, верхней нет — среди аккуратно диапазонированных соседей (`typing_per_char_ms` ограничен `0..200`). Без потолка:

- `/set typing_max_ms 600000` проходит кросс-полевую валидацию (`typing_min_ms <= typing_max_ms` выполнено) и вставляет **10-минутную паузу перед каждым ответом**;
- `typing_max_ms` вдобавок **переопределяет собственный «жёсткий потолок»**: `compute_typing_delay_ms` возвращает `min(delay, max(TYPING_HARD_CAP_MS, typing_max_ms))` (`app/handlers/_helpers.py:38`), то есть 4-секундный предел поднимается до того, что попросили в конфиге. Поведение намеренное и запиннено тестом — но именно оно превращает отсутствие потолка из «странно» в «бот замолкает».

O5 закрыт сужением `/set`/`/setprob` до `OWNER_ID`, поэтому вектора чужого чат-админа больше нет. Остаются две живые причины: те же парсеры использует `load_settings`, то есть опечатка в `.env` (лишний ноль) проходит молча, и владелец может выстрелить себе в ногу через `/set` без единого предупреждения. Ровно на этом классе уже обжигались: NaN проходил валидацию 37 ручек из 64 (закрыто PR #101) — тот же корень, «валидация пропускает то, о чём её не спросили».

## What Changes

- Пяти ручкам без потолка задаются верхние границы: `typing_max_ms`, `min_cooldown_sec`, `min_tokens_for_model`, `reply_burst_boost_sec`, `reply_burst_suppress_sec`.
- Границы выбираются по осмысленному рабочему диапазону, а не по типу данных; обоснование каждой — в `design.md`.
- Значение вне диапазона отвергается **одинаково** и в `/set`, и при загрузке `.env` — без тихой подстановки дефолта.
- **BREAKING** для конфигураций, где такое значение уже стоит: бот откажется стартовать с `.env`, который раньше принимался. Это намеренно — молчаливый старт с 10-минутной паузой хуже явного отказа. Живой `.env` проверяется перед выкаткой (задача в `tasks.md`).
- Взаимодействие `typing_max_ms` с `TYPING_HARD_CAP_MS` **не меняется**: потолок ручки просто перестаёт быть бесконечным. Переделка самого правила «конфиг поднимает hard cap» — отдельный разговор, здесь не решается.

## Impact

- **Код**: `app/config/registry.py` (объявления пяти `FieldSpec`), при необходимости `.env.example` (документирование диапазонов).
- **Совместимость**: старт с значением вне нового диапазона падает с явной ошибкой; `/set` возвращает отказ с описанием диапазона (механика сообщения уже есть — `Domain.description`).
- **Тесты**: `tests/test_registry*.py` — на каждую из пяти ручек по паре «в диапазоне / за диапазоном», плюс проверка, что отказ приходит из обоих путей (`/set` и `load_settings`).
- **Риск регресса**: ненулевой у `typing_max_ms` — есть тест, пиннящий подъём hard cap; выбранный потолок обязан оставлять этот тест зелёным.
