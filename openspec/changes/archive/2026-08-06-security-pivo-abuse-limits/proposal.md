## Why

`/pivo` — единственная команда, намеренно исключённая из ограничения частоты: её суточная квота считалась достаточным лимитом. Квота ограничивает **успешные** вызовы, но не отказы. Сейчас каждый вызов сверх квоты по-прежнему приводит к ответу бота в чат («Лимит /pivo на сегодня исчерпан»), поэтому один участник, повторяя команду, получает неограниченный поток сообщений от бота — ровно та амплификация трафика и риск флуд-ограничений Telegram, ради которых кулдауны и вводились.

Рядом лежат три смежных дефекта того же лимитирующего слоя:

- сообщение собирается **до** списания квоты, поэтому отклонённый вызов всё равно оплачивается чтением подписчиков и расшифровкой их данных;
- аргументы команды не ограничены по длине, и достаточно длинный «повод» делает итоговое сообщение длиннее лимита Telegram — отправка падает всегда, а вызов повторяем;
- превышение лимита на число упоминаний ломает команду не для нарушителя, а для всего чата и навсегда: 21-й подписавшийся делает `/pivo` неработающим до `/clear confirm`, потому что лимит реализован как отказ вместо усечения.

## What Changes

- Уведомление об исчерпанной суточной квоте `/pivo` ограничивается по частоте: одно сообщение на пару «участник — чат» в окно (60 с), дальнейшие попытки внутри окна остаются без ответа. Объяснение сохраняется, поток сообщений — нет.
- Квота списывается **до** сборки сообщения: отклонённый вызов больше не читает подписчиков и не расшифровывает их данные. Возврат квоты при последующем сбое отправки сохраняется.
- Аргументы `/pivo` ограничиваются по длине (повод — 200 символов, время — 40): длинный ввод усекается, итоговое сообщение гарантированно укладывается в лимит Telegram.
- **BREAKING (наблюдаемое поведение):** превышение лимита на число упоминаний больше не отменяет вызов. Список получателей усекается до лимита, а в сообщение добавляется пометка о том, что упомянуты не все. Команда перестаёт быть выключаемой из чата простым набором подписчиков.
- Пост-обработка после доставки сообщения (запись анти-повтора, лог, отчёт владельцу) перестаёт ронять обработчик: её сбой логируется, но вызов остаётся выполненным.

## Capabilities

### New Capabilities
- `pivo-call-limits`: собственные лимиты команды `/pivo` — суточная квота и порядок её списания, ограничение аргументов, ограничение числа получателей и поведение при его превышении.

### Modified Capabilities
- `command-rate-limits`: требование «отказ по умолчанию молчаливый» распространяется на отказы по собственным лимитам команды, а не только на отказы по окну частоты. Сегодня уведомление о превышении собственного лимита ничем не ограничено и само становится потоком сообщений.

## Impact

- **Код**: `app/handlers/pivo.py` (порядок списания квоты, дросселирование уведомления, устойчивая пост-обработка), `app/services/pivo_service.py` (усечение списка получателей вместо исключения), `app/services/pivo_parser.py` или `app/services/pivo_message_builder.py` (ограничение длины аргументов).
- **Поведение**: пользователь, исчерпавший квоту, получает объяснение один раз в окно вместо каждого раза; чат с числом подписчиков больше лимита продолжает получать `/pivo` с усечённым списком.
- **Совместимость**: `PivoCallLimitError` остаётся для явных упоминаний (их указывает сам вызывающий, и молчаливое усечение чужого ввода скрыло бы, что часть людей не позвана).
- **Тесты**: повторный вызов сверх квоты не порождает второго ответа; отклонённый по квоте вызов не читает подписчиков; длинный аргумент усекается и сообщение укладывается в лимит; при числе подписчиков выше лимита сообщение уходит с пометкой об усечении; сбой пост-обработки не ломает вызов.
- **Документация**: README (раздел `/pivo`), `.env.example` (описание `PIVO_SUBSCRIBER_FANOUT_LIMIT` — теперь это порог усечения, а не отказа).
