## Context

См. `proposal.md` — Why. Здесь только то, что определяет форму починки.

Сброс идёт по цепочке `cmd_set` (`app/handlers/admin.py`) →
`LearningService.reset_short_layer(chat_id | None)` →
`Database.reset_short_layer(chat_id | None)`. `None` означает «все чаты» и
выполняется как `UPDATE … SET s_value = 0` без `WHERE` по четырём таблицам.

Переопределения живут только в памяти: `RuntimeState.chat_overrides:
dict[int, dict[str, Any]]` на базовом состоянии, до рестарта. Поэтому набор
чатов с оверрайдом ключа полон и известен хендлеру в момент команды — читать
его из БД не нужно и негде.

Глобальная ветка хендлера уже сравнивает новое значение с **базовым**
(а не с эффективным у чата вызова) — эта логика остаётся как есть.

## Goals / Non-Goals

**Goals:**

- При глобальной смене сбрасываются ровно те чаты, чей эффективный период
  изменился.
- Счётчик сохранённых чатов виден в ответе на команду; ID чатов — нет.
- Пер-чатовые формы и `reset_short_layer(<chat_id>)` не меняются.

**Non-Goals:**

- Не трогать поведение при рестарте (оверрайды не переживают рестарт — после
  него все чаты живут по глобальному значению, спорить не о чем).
- Не заводить персистентный реестр оверрайдов.
- Не менять инвалидацию кэшей генератора: сбросить все кэши при глобальной
  смене по-прежнему безопасно и проще, чем считать, чьи именно.

## Decisions

**Р1. Исключения вычисляет хендлер и передаёт вниз списком.**
`reset_short_layer(None, exclude=<chat_ids>)` в сервисе и БД. Альтернатива —
дать `LearningService` ссылку на `RuntimeState` и вычислять внутри — тянет
конфиг в сервис обучения, у которого этой зависимости сейчас нет. Хендлер уже
держит `runtime_state_base` и уже читает `chat_overrides` для проверки
конфликтов (`registry.py`), так что источник тот же.

**Р2. В БД исключение — `WHERE chat_id NOT IN (…)` с параметрами.**
Пустой список = прежний запрос без `WHERE`. Альтернатива — цикл по чатам с
пер-чатовым сбросом — требует знать полный список чатов из БД, лишний запрос
и лишняя транзакция ради того, что SQL делает одной строкой.

**Р3. Пер-чатовый сброс (`chat_id` задан) не принимает исключений.**
Параметр только для формы «все чаты»; при заданном `chat_id` непустой
`exclude` — ошибка вызова, а не тихое объединение семантик.

**Р4. Текст предупреждения дополняется одной строкой со счётчиком** и только
когда счётчик больше нуля: «N чат(ов) со своим периодом сохранили слой».

## Risks / Trade-offs

- [Чат с оверрайдом, равным **старому** глобальному значению] → его
  эффективное значение при глобальной смене тоже не меняется (оверрайд
  держит старое число), слой сохраняется — это правильно: масштаб у него
  прежний. Отдельной ветки не нужно.
- [Список исключений длинный] → `NOT IN` с параметрами ограничен лимитом
  SQLite на число переменных (999/32766); число чатов с оверрайдом
  ограничено политикой `in-memory-state-eviction` и на порядки меньше.
- [Оверрайд снят позже через `/set reset`] → существующая ветка сравнивает
  глобальное значение с прежним эффективным и сбрасывает чат тогда — без
  правки.
