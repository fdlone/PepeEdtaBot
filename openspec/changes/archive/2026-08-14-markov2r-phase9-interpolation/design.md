## Context

Мотивация — `proposal.md` → «Why». Требования — `specs/`. Здесь только то, что
нужно для выбора реализации; спецификация фазы —
`docs/v2/M2R_PHASE9_INTERPOLATION.md`, промпт — `PROMPT_phase9_implementation.md`.

Что уже есть в коде и определяет форму решения:

1. **Точка внедрения одна.** В `_run_generation_loop`
   (`app/core/markov.py`) ветка `if pool3 and order >= 3:` — единственное место,
   где шаг берётся из существующего состояния order-3. Проекция `(w2, w3)`
   читается там же и уже сегодня: валвом order-mix через `self._get2(chat_id, w2, w3)`.
2. **Слои кэшируются раздельно** — `_get3` и `_get2` с LRU по ключу состояния.
   Это ровно та схема, которую промпт называет предпочтительной: сливать при
   чтении, не кэшировать слитое.
3. **Механизм «нормализованные веса вместо счётчиков» уже существует.**
   `TemporalBlend.blend` возвращает `BlendedPool(weights, displacement)`,
   выровненный по тем же строкам, а `weighted_next_choice` принимает их через
   `base_weights` и переключает пол веса с 0.01 на 1e-12. То есть путь «пул +
   нормализованное распределение» проложен и протестирован.
4. **`TransitionRow = tuple[str, int, float, int | None]`** — токен, долгий
   счётчик, короткий счётчик, метка времени. Оба чтения переходов приходят
   упорядоченными по токену, и на это опирается документированное предусловие
   `weighted_next_choice`.

## Goals / Non-Goals

**Goals:**

- Смешивание, структурно неспособное сработать при β = 0: ранний return до
  чтения проекции, по образцу `TemporalBlend.enabled`.
- Один путь построения весов шага, а не второй параллельный: интерполяция
  отдаёт то же, что бленд — пул плюс нормализованные веса.
- Композиция с блендом определена, а не случайна.
- Гейт пре-регистрирован до любого прогона.

**Non-Goals:**

- Не кэшируем слитое распределение (и потому не заводим β в ключи кэша).
- Не меняем путь бэкоффа, фильтры, скоринг, best-of-N, схему БД.
- Не реализуем M2R-910/920/930.
- Не прогоняем грид и не проводим ручной раунд: гейт регистрируется, но не
  расходуется.

## Decisions

### D1. Отдельный модуль по образцу `TemporalBlend`, а не ветка внутри цикла

Заводится `app/core/interpolation.py` с конфигурацией `OrderInterpolation(beta)`
и методом слияния, возвращающим `InterpolatedPool | None`. `None` — контракт
нейтральности: при β = 0 вызывающий продолжает работать с чистым `pool3`, и
никакой арифметики не происходит. Это буквально та же форма, которой Phase 3
добилась побайтной нейтральности, и она уже проверена гардом хеша.

Альтернатива — inline-ветка в `_run_generation_loop`. Отвергнута: цикл уже
несёт валв order-mix, бленд, энтропию и дедуп; ещё одна ветка там не тестируема
отдельно, а слияние распределений — ровно та логика, которую надо покрывать
unit-тестами без поднятия генератора.

### D2. Слияние по объединению токенов, порядок — по токену

Оба входных пула упорядочены по токену, поэтому слияние идёт линейным проходом
по объединению и результат упорядочен по токену без сортировки.

**Осознанное отклонение от промпта.** Промпт требует «первичный ключ — убывание
веса, вторичный — лексикографический по токену». Это противоречит
документированному предусловию `weighted_next_choice` («items упорядочены по
токену», `markov.py:889`), от которого зависит и валв order-mix, и
`transition_was_available`. Требование промпта по существу — **детерминизм**
порядка, и он выполняется токен-порядком полностью; введение второго,
конфликтующего порядка на том же пути дало бы расхождение, которое потом
диагностируется как дрейф поведения. Берём токен-порядок.

### D3. Композиция с временнóй смесью: каждый слой нормализуется своим способом

Вклад слоя в слияние — его **нормализованное** распределение. Если бленд
включён, нормализация слоя берётся из бленда (он уже возвращает распределение);
если выключен — из сырых счётчиков, нормированных в пуле слоя.

Так интерполяция не конкурирует с блендом за одну точку, а надстраивается над
ним: бленд отвечает на «как взвесить кандидатов внутри слоя», интерполяция — на
«как сложить два слоя». Обе ручки нейтральны по дефолту, и одновременное
включение — не отгружаемая конфигурация; но поведение определено, а не оставлено
на случай.

### D4. Пол веса и путь `base_weights`

Слитый результат — распределение, а не счётчики, поэтому он идёт в
`weighted_next_choice` через `base_weights`, где пол веса уже переключён на
1e-12. Пол 0.01, откалиброванный под счётчики ≥ 1, сплющил бы хвост
распределения в плато — это уже разобрано в комментарии функции для бленда, и
интерполяция попадает в тот же класс.

### D5. Телеметрия: доля добавивших шагов и TV-дистанция

Два счётчика по образцу `blend_step_coverage` / `mean_blend_displacement`.
«Добавил кандидата» считается по факту появления токена, которого не было в
`pool3` — это отличает «механизму не на чем работать» (разреженность до дна) от
«механизм выключен». TV-дистанция считается против чистого P3 на объединении
токенов.

### D6. Порт не расширяется

Проекция `(w2, w3)` — это `get_transitions`, который в порту уже объявлен и уже
вызывается (валв order-mix, путь бэкоффа). Правило «порт объявляет ровно то, что
вызывается» соблюдено без правок, `tests/test_layering.py` не затрагивается.

## Risks / Trade-offs

- **Словесный салат при β > 0** → ships-disabled; ручной раунд в гейте; откат
  через `/set` без рестарта; β — плавная ручка, а не переключатель.
- **Латентность: слияние на каждом шаге** → слияние O(k) по кандидатам, k мал
  (пулы — единицы строк); чтение проекции идёт через тот же LRU, что валв
  order-mix, то есть на большинстве шагов это кэш-хит. Бюджет p95 — условие
  гейта, а не надежда.
- **β = 0 перестанет быть байт-идентичным при неаккуратной правке** → регресс
  `generation_hash` в тестах фазы плюс уже существующий CI-гард на синтетическом
  снапшоте.
- **Условие 6 гейта ссылалось на инструмент, которого нет** — панель из ≥3
  рейтеров с Fleiss' kappa ≥ 0.4, тогда как роадмап §3 фиксирует недоступность
  панели (Phase 4: kappa 0.17 на случайной панели). **Решено владельцем
  2026-08-14, до регистрации гейта:** содержательный порог остаётся дословно
  («доля связных не ниже C0 более чем на 10 п.п.»), измерительный инструмент
  меняется на соло-протокол M3R-020 с порогом валидности по
  само-консистентности (≥20% выборки повторно, согласие с собой ≥ 0.8).
  Правка законна по правилам пре-регистрации: запрещено менять пороги **после**
  того, как данные увидены, а не чинить ссылку на несуществующий инструмент до
  прогона. Это починка рассинхрона документов — роадмап обновился после вывода о
  панели, спека фазы нет.
  **Следствие, внесённое в роадмап §5:** промоушен β поимённо зависит от
  существования тулинга M3R-020, то есть соло-протокол поднимается в ту же
  волну. Сам M3R-020 в объём этой фазы не входит.

## Migration Plan

Схема БД не меняется, миграций нет. Ручка приезжает с дефолтом 0, поэтому
развёртывание фазы не меняет поведения: включение — отдельное решение по итогам
гейта. Откат — `/set` в ноль, без рестарта и без последствий для накопленных
данных.
