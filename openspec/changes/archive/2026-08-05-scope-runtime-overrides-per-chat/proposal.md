## Why

O5 закрыт 2026-07-22 интерим-фиксом: `/set` и `/setprob` сужены до `OWNER_ID` новым фильтром `OwnerOnly`, чужой чат-админ больше не может задеть настройки. Вектор безопасности закрыт — но причина, по которой он вообще существовал, осталась: **`RuntimeState` один на процесс**. `/set` от владельца по-прежнему меняет генерацию сразу во всех чатах.

Практическое следствие: тюнинг невозможен без побочного эффекта. Владелец не может подкрутить один чат, не изменив поведение бота во всех остальных, — а весь трек работы над генерацией состоит из осторожных точечных изменений с окнами наблюдения (см. историю групп A/B в `docs/CLOSED.md`). Сейчас окно наблюдения одного чата автоматически становится окном всех чатов, и любой результат смешивается.

Это задача про удобство и чистоту эксперимента, **не про безопасность**: без неё дыры уже нет. Оценка из бэклога — день-полтора с тестами; она не «быстрая правка» по трём причинам, которые и делают её достойной отдельного разбора:

- ~58 полей `runtime_state.X` читаются напрямую в четырёх файлах (`response_generator.py`, `admin.py`, `learning.py`, `_helpers.py`);
- `registry.try_apply` валидирует кросс-полевые инварианты (`typing_min<=max`, `mood_sleepy<lively`, `reply_probability_min<=max`) на копии стейта — при оверлее валидировать нужно против значений **конкретного чата**, иначе допустимая для чата комбинация будет отвергнута по глобальным значениям или наоборот;
- `RuntimeState` держит не только настройки, но и живое состояние по чатам (`last_reply_ts`, `recent_replies`, `chat_mood`, …) — оверлей обязан оставить его общим, иначе бот забудет, что уже говорил.

## What Changes

- Появляется **оверлей настроек по чату** поверх глобальных значений: чат, для которого оверлей не задан, ведёт себя ровно как сегодня.
- `/set` и `/setprob` меняют настройки **того чата, где вызваны**; способ изменить глобальное значение сохраняется явной формой команды.
- Кросс-полевые инварианты проверяются против **эффективных значений конкретного чата**, а не глобальных.
- `/config` показывает значения, действующие в текущем чате, и отмечает, какие из них переопределены.
- Оверлей ограничен по времени и объёму — по той же политике, что соседние состояния по чатам (`prune_inactive`), чтобы не завести новый неограниченный рост.
- Живое состояние по чатам (счётчики, истории ответов, настроение) остаётся **общим и неразделённым** — оверлей касается только настроек.
- **BREAKING** для привычки владельца: `/set` перестаёт быть глобальным по умолчанию. Это и есть цель изменения, но старое поведение должно оставаться достижимым одной явной командой.

## Impact

- **Код**: `app/config/runtime_state.py` (оверлей и его вытеснение), `app/config/registry.py` (`try_apply` против эффективных значений чата), `app/handlers/admin.py` (`/set`, `/setprob`, `/config`), и все места, читающие настройки напрямую: `app/core/response_generator.py`, `app/handlers/learning.py`, `app/handlers/_helpers.py`.
- **Риск регресса — главный в этой задаче**: ~58 полей на горячем пути генерации. Пропущенное место чтения не падает, а тихо продолжает брать глобальное значение. Как это ловится — в `design.md`.
- **Производительность**: чтение настройки на горячем пути не должно стать дороже; способ достижения (снимок настроек на генерацию вместо разыменования на каждое поле) разбирается в `design.md`.
- **Тесты**: `tests/test_registry*.py`, `tests/test_handlers.py` — оверлей применяется только к своему чату, инварианты считаются по эффективным значениям, живое состояние остаётся общим, вытеснение работает; плюс проверка поведенческой нейтральности для чата без оверлея.
- **Документация**: README (форма команд `/set`, `/setprob`, вывод `/config`), `docs/OPEN.md` — пункт уходит из бэклога.
