## Context

Мотивация — `proposal.md`, требования — `specs/chat-scoped-settings/spec.md`.

Три факта из кода определяют весь подход:

1. **Живое состояние по чатам целиком словарное.** `last_reply_ts`, `learned_messages`, `recent_replies`, `chat_mood`, `recent_reply_times`, `last_mention_reply_ts`, `rare_events_today`, `last_user_quirk_day`, `_last_chat_activity` — все `dict`, ключ — `chat_id` или пара. Значит, поверхностная копия `RuntimeState` **разделяет** это состояние по ссылке: мутации через копию видны в оригинале. Требование спеки «оверлей не разделяет живое состояние чатов» выполняется само собой, а не отдельной механикой.
2. **Настройки мутируются ровно в одном файле.** Единственное прямое присваивание полю настройки во всём `app/` — `runtime_state.reply_probability = value` в `app/handlers/admin.py:130` (`/setprob`); всё остальное идёт через `registry.try_apply`. То есть точек записи две, а не 58.
3. **Чтений — ~58, и они разбросаны** по `response_generator.py`, `admin.py`, `learning.py`, `_helpers.py`. Именно это делало задачу «день-полтора»: править каждое место чтения дорого и, главное, ненадёжно — пропущенное место не падает, а тихо берёт глобальное значение.

Из (1) и (3) следует главная идея: **не трогать места чтения вовсе**.

## Goals / Non-Goals

**Goals:**

- Переопределения по чату при неизменных местах чтения настроек.
- Доказанная поведенческая нейтральность для чата без переопределений — не заявленная, а измеренная.
- Ограниченный рост нового состояния с первого дня.

**Non-Goals:**

- Не сохраняем переопределения между рестартами. Настройки живут в памяти и сегодня; персистентность — отдельное решение с миграцией и своим набором вопросов.
- Не разделяем живое состояние по чатам иначе, чем оно разделено сейчас.
- Не расширяем круг тех, кто может менять настройки: обе формы команд остаются owner-only (фикс O5).
- Не выносим наружу «профили настроек» и шаблоны — сначала базовый механизм.

## Decisions

### D1. Эффективный снимок подставляется мидлварью, места чтения не меняются

`RuntimeState` кладётся в контекст aiogram (`dp["runtime_state"]`) и раздаётся хендлерам как аргумент. Добавляем мидлварь, которая для каждого апдейта подменяет `runtime_state` на **эффективный для этого чата** экземпляр:

- у чата нет переопределений → в контекст идёт **тот же самый объект**, что и сегодня (не копия), — нулевая цена и побайтово прежнее поведение;
- есть переопределения → поверхностная копия с применёнными полями; словари живого состояния разделяются по ссылке (факт 1), поэтому анти-повтор, настроение и счётчики продолжают работать так же.

Это одна точка вместо 58. Альтернативы:

- **Править каждое место чтения на `effective(chat_id).X`.** Отклонено: дорого и ненадёжно — пропуск не проявляется как ошибка.
- **Прокидывать `chat_id` в генератор и читать через аксессор.** Отклонено: меняет сигнатуры горячего пути ради того же результата и ломает недавно наведённый порядок с keyword-only параметрами (PR #102).

### D2. Запись идёт в базовое состояние, а не в снимок

Мидлварь оставляет базовый экземпляр доступным отдельным ключом. `/set`, `/setprob` и `/config` работают с ним явно: первые два пишут в оверлей нужной области (чат или глобально), третий читает оба слоя, чтобы отметить переопределённые значения.

Без этого `/set` записал бы значение в копию, отвечающую «готово», и потерял бы его на следующем апдейте — самый вероятный способ сделать эту задачу тихо неработающей.

### D3. Кросс-полевые проверки — против эффективных значений чата

`registry.try_apply` уже устроен правильно по форме: парсит, кладёт значение на копию, валидирует копию, и только потом пишет в реальный объект. Меняется лишь то, **что за копия**: для переопределения по чату это копия эффективного состояния этого чата, для глобального изменения — глобального.

Это прямо покрывает сценарий спеки «допустимо для чата, недопустимо глобально»: например, `typing_min_ms` из переопределения чата и новый `typing_max_ms` образуют допустимую пару, хотя с глобальным `typing_min_ms` не образовали бы.

### D4. Оверлей вытесняется вместе с остальным состоянием чата

Оверлей — это ещё один `dict` по `chat_id` на `RuntimeState`, поэтому он включается в существующие `prune_inactive` и `forget_chat`, а не заводит собственную политику. Именно так закрывается риск «новый неограниченный рост», отмеченный в бэклоге рядом с `_admin_cache`.

Следствие, которое надо принять сознательно: **переопределения неактивного чата исчезнут** — так же, как исчезает его настроение и история ответов. Для тюнинга живого чата это несущественно (чат активен по определению), а альтернатива — вечно растущий словарь.

### D5. Нейтральность доказывается хешем, а не осмотром

В проекте уже есть годный прецедент (PR #102): 1000 генераций (4 сида × 250) на прод-копии дают побайтово одинаковый вывод, SHA256 сверяется до и после. Тот же приём применяется здесь для пути «без переопределений»: если хеш совпал, значит ни одно из 58 мест чтения не начало брать другое значение и порядок потребления RNG не сдвинулся.

Для пути «с переопределениями» хеш не нужен — там поведение и должно отличаться; достаточно поведенческих тестов из спеки.

## Risks / Trade-offs

- **`/set` пишет в снимок и молча теряет значение** → D2; тест, который после `/set` проверяет значение на следующем апдейте, а не сразу в ответе команды.
- **Пропущенное место чтения** → снято по построению (D1): места чтения не меняются, а хеш из D5 подтверждает это измерением.
- **Цена копии на каждый апдейт** → для чатов без переопределений копии нет вовсе; для остальных это одна поверхностная копия дата-класса против ~80 мс генерации.
- **Мутация настройки через снимок в обход D2** (кто-то в будущем присвоит поле напрямую) → тест-сторож: единственные разрешённые точки записи в настройки — `try_apply` и обработчик `/setprob`.
- **Владелец забывает, что `/set` теперь локальный, и «чинит» глобальную настройку в одном чате** → ответ команды явно называет область изменения («в этом чате» / «глобально»), `/config` отмечает переопределённые значения.
- **Потеря переопределений при рестарте и при вытеснении** → принято сознательно (D4, Non-Goals); в README это фиксируется как свойство, а не как дефект.
