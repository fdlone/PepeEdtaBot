## Context

`generate_with_result`: seeded-маршрут кладёт кандидатов до цикла попыток
(бюджет `route_slot_budget`), затем цикл из `GENERATION_ATTEMPT_BUDGET`
попыток добирает пул до `effective_target`; `request.seed` (L1-затравка
конвейера, шанс 0.25) подаётся только первой попытке (`seed = None` в конце
итерации). Маршрут кандидата ставится на создании (`_ScoredCandidate.route`),
телеметрия считает `attempted / present / won`.

## Decisions

### D1. Маршрут — это попытки цикла, а не отдельная сборка

Seeded строит токены своим способом (реверсный индекс), поэтому у него своя
ветка. Hot-кандидат — обычная прогулка с `seed_tokens`; заводить для него
отдельную ветку значило бы продублировать финализацию, гейты, дописку и
мутации — ровно ту ловушку, которую чинил M3R-101. Поэтому маршрут занимает
**первые `hot_budget` попыток** цикла: каждая получает свою n-грамму и идёт
общим путём. Атрибуция `HOT` ставится по факту «попытка была с
затравкой маршрута», дописка её не перебивает (дописка — постобработка той
же прогулки; у seeded-кандидатов дописки нет по построению, здесь — есть, и
это первое отличие, о котором должен знать читатель разбивки).

Цена решения: «слот» — это попытка, а не гарантированный кандидат.
Отклонённая hot-попытка отдаёт место обходу автоматически (условие остановки
считает пул), а разница «маршрут запускался / положил кандидата / выиграл»
видна в трёх счётчиках телеметрии.

### D2. Каждый слот — своя n-грамма, без возврата, из ГСЧ генерации

Пул `get_hot` (top-8 по действующим `hot_ngram_min_count` /
`hot_ngram_recency_share`) читается один раз на генерацию; слоты выбирают
n-граммы без возврата — два слота с одной фразой дали бы две вариации одного
зачина, а не два кандидата. Розыгрыш идёт из `generation_rng` и только при
`hot_budget > 0`: при дефолте 0 ни одного обращения к ГСЧ и к базе —
байт-идентичность.

### D3. Только без контекста

Конвейер не сидирует адресованные ответы; маршрут наследует правило через
`request.context_tokens` — при непустом контексте `hot_budget = 0` и маршрут
в `attempted` не входит. Это то же условие, по которому харнесс моделирует
L1 только в noctx (`l1-hot-channel-sweep`, D1).

### D4. Легаси-затравка конвейера и маршрут

Когда маршрут включён и дал слоты, `request.seed` (одна n-грамма с шансом
0.25 на первую попытку) не используется: первые попытки заняты маршрутом, а
после них легаси-затравка не подаётся, как и раньше. Два механизма на одном
пуле путали бы атрибуцию; при `ratio = 0` легаси-путь не меняется.

### D5. Бюджет делится с seeded

`route_slot_budget` у каждого маршрута свой (потолок — половина пула); при
обоих включённых маршрутах обходу гарантирован хотя бы один слот при пуле 5
(2 + 2 + 1). Отдельного «общего бюджета маршрутов» не заводится: до первого
маршрутного грида это спекуляция, а инвариант «обход присутствует» держит тест.

## Замер

Гейт `l1_hot_channel` пре-регистрирован 2026-09-01, пороги не меняются:
coverage — доля успешных noctx-ответов со стартом победителя из затравки
(`start_source = "seed"`), must-improve `historical_meme_rate`, copy /
repetition не хуже, latency, связность. Грид `matrix_l1_route_grid.yaml`:
C7r20 / C7r40 при 2 / 0.25. Ожидание до прогона (записано здесь): при двух
слотах из пяти и 75% анкеровки coverage поднимется с ~2% до 15–20%; главный
риск — copy: затравка — корпусная фраза, а два кандидата из пяти — уже её
вариации.

## Хеш

Дефолт 0 ⇒ `hot_budget = 0`, ни розыгрыша, ни чтения, цикл попыток прежний.
Ожидание «сдвига нет» записывается в `hash-log.md` до правок.
