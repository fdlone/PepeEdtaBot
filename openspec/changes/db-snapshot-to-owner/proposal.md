# DB snapshot to owner

## Why

У владельца нет доступа к докеру и файловой системе прода, поэтому свежую
копию БД взять неоткуда — а она нужна постоянно: §7 `CLAUDE.md` велит мерить
на копии прода, M3R-001 невыполним на устаревшей копии (прецедент записан в
O11: «прод-копия старше выкаченной сборки»), приёмка `derive-phrase-index`
ждёт свежую копию прямо сейчас. Побочно проект получает офсайт-бэкап: сегодня
единственная копия данных живёт в докер-томе.

ЛС-канал владельцу уже существует (отчёты `/pivo`, алерты обслуживания) —
это единственный работающий путь доставки. Замер на текущей копии: БД
~12.9 МБ, в сжатом виде ~3.6 МБ при лимите Bot API 50 МБ — запас на годы.

## What Changes

- **На каждом старте процесса, до миграций**, снимается консистентный снимок
  БД (`VACUUM INTO`), сжимается gzip и отправляется документом в личку
  `OWNER_ID`. До миграций — потому что это одновременно точка отката, если
  миграция испортит данные, и вход для правила «каждую миграцию проверять на
  копии прода». Пересборка контейнера сама том не трогает; момент, когда новый
  код впервые встречает старые данные, — это старт нового процесса.
- **Отказ любой ступени не ломает запуск**: нет файла БД (первый старт), ЛС
  закрыт, файл перерос лимит, сеть — warning в лог, бот стартует дальше.
- **Owner-only команда `/db_snapshot` в личке** — свежий снимок по запросу,
  без рестарта. В групповых чатах команда не отвечает вовсе: файл с корпусом
  сообщений не должен иметь пути в группу.
- **Env-ручка `DB_SNAPSHOT_TO_OWNER`** (bool, дефолт `true`) — выключатель
  автоотправки на старте. Команда `/db_snapshot` от ручки не зависит: это
  явное действие владельца.
- `/db_snapshot` не попадает в меню команд (`TELEGRAM_COMMANDS`) и в кулдауны
  (`COOLDOWN_EXEMPT_COMMANDS`, та же причина, что у `pivo_check`/`quirk_stats`:
  owner-only, троттлить владельца против самого себя нечего).

## Capabilities

### New Capabilities

- `db-snapshot-delivery`: доставка консистентного снимка БД владельцу в личку —
  на старте процесса и по команде; границы приватности и отказов.

### Modified Capabilities

- `private-chat-diagnostics`: состав команд лички расширяется —
  `/ping`, `/help` и owner-only `/db_snapshot`; закрепляющий тест-инвентарь
  обновляется тем же изменением.

## Impact

- Код: новый модуль снимка (`app/services/db_snapshot.py` — VACUUM INTO +
  gzip + отправка), `main.py` (снятие до `db.init()`, фоновая отправка после
  создания `Bot`, `COOLDOWN_EXEMPT_COMMANDS`), хендлер `/db_snapshot`
  (`app/handlers/admin.py`), `app/config/settings.py` (`DB_SNAPSHOT_TO_OWNER`).
- Тесты: `TestPrivateChatCommandSurface` (инвентарь пополняется
  `db_snapshot: True`), пиннёные списки кулдаунов, `test_settings.py`
  (`SETTINGS_ONLY_ENV_VARS`), тесты модуля снимка и хендлера.
- Доки: `.env.example`, README (таблица команд).
- `generation_hash`: не задет по построению — ни один файл пути генерации не
  трогается (`main.py`, хендлеры и новый сервис в хеш не входят); снятие
  снимков не требуется.
- Privacy (§4 `CLAUDE.md`): в файле — открытый корпус чата; граница — только
  ЛС `OWNER_ID`, записана в спеку и держится фильтрами хендлера.
