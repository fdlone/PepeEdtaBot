# Design — db-snapshot-to-owner

## Context

Мотивация — `proposal.md`. Порядок старта (`main.py::run_bot`): `load_settings`
→ `db.init()` (миграции) → сервисы → `Bot(...)` → polling. ЛС-канал владельцу
уже существует (алерты обслуживания шлют `bot.send_message(owner_id, ...)` с
перехватом «chat not found»). Замер: БД ~12.9 МБ, gzip ~3.6 МБ, лимит
`sendDocument` — 50 МБ.

## Goals / Non-Goals

**Goals:** свежая копия прода у владельца с каждого рестарта и по запросу;
ноль влияния на надёжность запуска; граница «файл только в ЛС владельца».

**Non-Goals:** детекция «это была именно пересборка» (нужен build-SHA через
ARG и деплой-команду — бот про сборки не знает; рестарты редки, лишний снимок
при обычном рестарте — бесплатный бэкап); троттлинг автоотправки при
crash-loop (добавить меткой в БД, если станет проблемой); ротация/хранение
истории снимков (сторона получателя); поддержка БД > 50 МБ (chunking или
другой канал — отдельным решением, когда размер приблизится).

## Decisions

- **D1 — снимок до `db.init()`.** До миграций снимок — точка отката и вход
  для правила «миграцию проверять на копии прода»; после — уже состояние
  новой сборки, выводимое из первого прогоном мигратора. Файл читается
  короткоживущим соединением stdlib `sqlite3` в `asyncio.to_thread`
  (писателей до старта polling нет, `VACUUM INTO` даёт консистентный
  однофайловый снимок без -wal/-shm; голое копирование файла в WAL-режиме
  небезопасно и отвергнуто).
- **D2 — снятие сразу, отправка фоном.** Снимок снимается до миграций и
  лежит во временном файле; отправка (`gzip` + `send_document`) уходит в
  `asyncio.create_task` после создания `Bot`, чтобы не задерживать polling.
  Временные файлы удаляются в `finally` фоновой задачи.
- **D3 — отказоустойчивость по образцу алертов обслуживания.** Любое
  исключение ступени снимка/отправки → `logger.warning` (маскирование —
  свойство логгера, §4) и продолжение запуска. Отдельно: файл > 50 МБ →
  вместо документа владельцу уходит текстовое предупреждение о размере —
  молчаливое исчезновение бэкапа хуже сообщения.
- **D4 — команда без ручки.** `DB_SNAPSHOT_TO_OWNER` гасит только
  автоотправку: выключатель существует против шума на старте, а команда —
  явный запрос владельца, глушить её нечем и незачем. Фильтры регистрации:
  private-чат + `OwnerOnly` — в группах команда не зарегистрирована вовсе,
  файл с корпусом структурно не может уехать в группу.
- **D5 — env-only настройка, не ручка реестра.** По образцу `CHAT_TIMEZONE`:
  свойство деплоя. `SETTINGS_ONLY_ENV_VARS` в `test_settings.py` пополняется,
  `.env.example` — незакомментированной строкой с дефолтом `true` (тест
  дрейфа требует совпадения с кодовым дефолтом).
- **D6 — имя файла с датой:** `markov-YYYYMMDD-HHMMSS.db.gz` (UTC) — снимки в
  ЛС различимы без открытия; идентификаторов чатов в имени нет.

## Risks / Trade-offs

- [Корпус чата едет через серверы Telegram] → круг доступа не расширяется
  (владелец видит БД по определению, канал ЛС уже несёт отчёты `/pivo`);
  граница «только ЛС `OWNER_ID`» записана в спеку и держится фильтрами.
- [Автоотправка при каждом рестарте, не только при пересборке] → осознанный
  размен (Non-Goals): лишний снимок дешевле недополученного.
- [VACUUM INTO по команде на живой БД конкурирует с ответами] → операция
  ~13 МБ / доли секунды в worker-thread; команда owner-only и без окна —
  злоупотребить некому.

## Migration Plan

Обычный мерж; активируется на ближайшем редеплое без правок прод-env
(дефолт `true`). Откат — `DB_SNAPSHOT_TO_OWNER=false` или ревёрт. Перед
выкаткой владельцу стоит убедиться, что личный чат с ботом открыт (то же
условие, что у отчётов `/pivo`).
